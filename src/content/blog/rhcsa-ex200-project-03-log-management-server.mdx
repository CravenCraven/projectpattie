<div class="pp-brief"><p><span class="c-light">Scenario:</span> Your organization needs <code>logserver1.lab.example.com</code> set up as a centralized logging and monitoring server. You provision dedicated LVM storage for logs, configure rsyslog to receive logs from remote systems, write monitoring scripts, schedule health checks, manage and harden services, deploy a container-based log viewer, and make sure everything survives a reboot.</p><p><span class="c-light">Domains Covered:</span> All 6 (D1 through D6)</p><p><span class="c-light">Estimated Time:</span> 90–120 minutes</p><p><span class="c-light">Difficulty:</span> Exam-level</p><p><span class="c-light">Rule:</span> Every configuration must survive a reboot. <div class="pp-note"><strong>note:</strong> You need a clean RHEL 9 VM with root access, one extra disk at <code>/dev/sdb</code> of at least 5 GiB (Task 1 uses 3.5 GiB and Task 10 extends the volume by another 1 GiB), and internet access. <code>dnf</code> and <code>podman pull</code> fetch packages and one public image (<code>ubi9/ubi</code>, no login required). This server is configured to receive logs from remote hosts, so the per-host files under <code>/var/log/remote</code> only appear once real clients send logs to it. That is expected.</div>

<div class="pp-part" id="p1">Part 1: The Exam<small>Attempt every task on your own first. Every configuration must survive a reboot.</small></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 1: Provision dedicated log storage</h3><div class="pp-domain">Domain 4 + Domain 5</div><p>Create a 3 GiB LVM Logical Volume named <code>lv&#95;logs</code> in a new Volume Group <code>vg&#95;logs</code> using <code>/dev/sdb</code>. Format it as XFS. Mount it persistently at <code>/var/log/remote</code> using its UUID in <code>/etc/fstab</code>. Set ownership to <code>root:root</code> and permissions to <code>755</code>.</p><p>Also create a 512 MiB Logical Volume named <code>lv&#95;archive</code> in the same VG. Format as XFS and mount persistently at <code>/var/log/archive</code>.</p></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 2: Configure rsyslog to receive remote logs</h3><div class="pp-domain">Domain 6</div><p>Configure rsyslog to:</p><ul><li>Listen for incoming UDP syslog messages on port 514</li><li>Listen for incoming TCP syslog messages on port 514</li><li>Write incoming logs from each remote host into a separate file: <code>/var/log/remote/%HOSTNAME%.log</code></li><li>Restart rsyslog and verify it is listening on port 514</li></ul><p>Open port 514 (both UDP and TCP) permanently in firewalld.</p></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 3: Configure rsyslog log rotation</h3><div class="pp-domain">Domain 6</div><p>Create a logrotate configuration file at <code>/etc/logrotate.d/remote-logs</code> that:</p><ul><li>Rotates all files matching <code>/var/log/remote/&#42;.log</code></li><li>Rotates daily</li><li>Keeps 30 days of logs</li><li>Compresses rotated logs</li><li>Skips rotation if the log file is empty</li><li>Runs <code>systemctl restart rsyslog</code> after rotation as a postrotate script</li></ul></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 4: Write a disk usage alert script</h3><div class="pp-domain">Domain 2</div><p>Create an executable script at <code>/usr/local/bin/disk&#95;alert.sh</code> that:</p><ul><li>Accepts a threshold percentage as its first argument (default to 80 if not provided)</li><li>Checks disk usage on <code>/var/log/remote</code> and <code>/var/log/archive</code></li><li>For each filesystem, if usage is at or above the threshold, prints: <code>ALERT: /path is N% full</code></li><li>If usage is below threshold, prints: <code>OK: /path is N% full</code></li><li>Logs all output with a timestamp to <code>/var/log/disk&#95;alerts.log</code></li><li>Exits with code 1 if any filesystem is above threshold, 0 if all are OK</li></ul></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 5: Write a log summary script</h3><div class="pp-domain">Domain 2</div><p>Create an executable script at <code>/usr/local/bin/log&#95;summary.sh</code> that:</p><ul><li>Accepts a hostname as its first argument</li><li>If no argument is given, summarizes all files in <code>/var/log/remote/</code></li><li>For each log file, counts and prints the number of lines containing <code>error</code>, <code>warning</code>, and <code>critical</code> (case-insensitive)</li><li>Outputs in the format: <code>hostname: errors=N warnings=N critical=N</code></li><li>Saves the summary to <code>/var/log/summary&#95;YYYYMMDD.txt</code></li></ul></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 6: Schedule monitoring tasks</h3><div class="pp-domain">Domain 6</div><ol><li>Schedule <code>disk&#95;alert.sh</code> to run every 30 minutes via a root crontab entry</li><li>Schedule <code>log&#95;summary.sh</code> to run every day at midnight via a root crontab entry</li><li>Create a systemd service <code>/etc/systemd/system/log-monitor.service</code> that runs <code>disk&#95;alert.sh 90</code> at boot</li><li>Create a systemd timer <code>/etc/systemd/system/log-monitor.timer</code> that triggers <code>log-monitor.service</code> every hour</li><li>Enable and start the timer</li></ol></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 7: Manage and harden services</h3><div class="pp-domain">Domain 3</div><p>Ensure the following service states and verify each survives a reboot:</p><ul><li><code>rsyslog</code>: active and enabled</li><li><code>firewalld</code>: active and enabled</li><li><code>chronyd</code>: active and enabled</li><li><code>cups</code>: stopped and disabled</li><li><code>avahi-daemon</code>: stopped and disabled</li></ul><p>After making changes, check for any failed units with <code>systemctl list-units --state=failed</code> and write the output to <code>/root/failed&#95;units.txt</code>.</p></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 8: Configure log archiving with ACLs</h3><div class="pp-domain">Domain 5</div><p>Create the group <code>logadmins</code> (GID 8000) and users <code>logadmin1</code> (UID 8001) and <code>logadmin2</code> (UID 8002), both with primary group <code>logadmins</code> and no login shell.</p><p>Set the following on <code>/var/log/archive</code>:</p><ul><li>Ownership: <code>root:logadmins</code></li><li>Permissions: <code>750</code></li><li>ACL: give <code>logadmin1</code> read/write/execute, <code>logadmin2</code> read/execute only</li><li>Default ACL: new files inherit read/write for <code>logadmins</code> group</li></ul><p>Verify with <code>getfacl /var/log/archive</code>.</p></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 9: Deploy a container-based log viewer</h3><div class="pp-domain">Domain 6</div><p>As root, pull <code>registry.access.redhat.com/ubi9/ubi:latest</code>. Run a detached container named <code>logviewer</code> that:</p><ul><li>Mounts <code>/var/log/remote</code> on the host to <code>/logs</code> inside the container (use <code>:Z</code> for SELinux)</li><li>Maps host port <code>9090</code> to container port <code>80</code></li><li>Sets environment variable <code>LOG&#95;DIR=/logs</code></li><li>Runs <code>sleep infinity</code></li></ul><p>Generate a systemd unit file, place it in <code>/etc/systemd/system/</code>, enable it so it starts at boot.</p></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 10: Extend log storage online</h3><div class="pp-domain">Domain 4 + Domain 5</div><p>The <code>lv&#95;logs</code> volume is getting full. Extend it by 1 GiB without unmounting or losing any data. Resize the XFS filesystem online using <code>xfs&#95;growfs</code>. Verify the new size with <code>df -h /var/log/remote</code>.</p></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 11: Configure NTP, hostname, and boot target</h3><div class="pp-domain">Domain 6</div><p>Set the system hostname to <code>logserver1.lab.example.com</code>. Set the default boot target to <code>multi-user.target</code>. Verify all settings after reboot.</p></div>

<h2 id="wt-01" class="pp-h2">Task 1: Provision dedicated log storage</h2>

<div class="pp-domain">Domain 4 + Domain 5</div>

<div class="pp-deepdive"><div class="pp-deepdive-label">// deep dive</div><p>Putting incoming logs on their own logical volumes is a deliberate isolation choice. If remote hosts flood this server, the worst case is that <code>/var/log/remote</code> fills up; the root filesystem, and therefore the ability to log in and fix the problem, stays healthy. This is the same reasoning behind giving <code>/var</code> or <code>/home</code> separate volumes in production.</p><p>The mechanics are the standard LVM stack: a physical volume initialises the disk for LVM, a volume group pools that space, and logical volumes are carved out of the pool. Because both volumes come from one <code>vg&#95;logs</code>, they draw from a shared pool, which is what lets Task 10 hand more space to <code>lv&#95;logs</code> later without touching the disk. That only works if you leave free extents in the group, so a 5 GiB disk holding a 3 GiB and a 512 MiB volume keeps room to grow.</p><p>Mount by <code>UUID</code> rather than device path. Device names like <code>/dev/sdb</code> can shift if disks are added or reordered, but a filesystem UUID is stable, so the fstab entry stays correct across reboots.</p></div>

<p><b>Goal:</b> Two LVM volumes in a new <code>vg&#95;logs</code>: a 3 GiB <code>lv&#95;logs</code> at <code>/var/log/remote</code> and a 512 MiB <code>lv&#95;archive</code> at <code>/var/log/archive</code>, both persistent.</p><h4 class="pp-step">Step 1.1: Create the volume group and logical volumes</h4><div class="pp-code"><div class="pp-code-head"><div Every active service is a potential attack surface and a consumer of resources, so a logging server has no business running a print spooler (<code>cups</code>) or a desktop discovery daemon (<code>avahi-daemon</code>).</p><p>The distinction that trips people up is <code>start</code>/<code>stop</code> versus <code>enable</code>/<code>disable</code>. <code>start</code> and <code>stop</code> act on the running system right now; <code>enable</code> and <code>disable</code> control whether the unit comes up at boot. <h2 id="wt-08" class="pp-h2">Task 8: Configure log archiving with ACLs</h2>

<div class="pp-domain">Domain 5</div>

<div class="pp-deepdive"><div class="pp-deepdive-label">// deep dive</div><p>Standard permissions cannot express what this task needs: two accounts in the same group that must have different access to the same directory. That is precisely the job of POSIX ACLs, which add named entries beyond the single owner, group, and other.</p><p>The service accounts come first. <code>logadmin1</code> and <code>logadmin2</code> exist to own access, not to log in, so they get <code>-s /sbin/nologin</code>, a shell that refuses interactive sessions. Their group <code>logadmins</code> owns the directory, and the base mode <code>750</code> gives the owning group read and execute while shutting out everyone else.</p><p>On top of that, named ACLs split the two users: <code>u:logadmin1:rwx</code> can write, <code>u:logadmin2:r-x</code> can only read. The <code>-d</code> (default) ACL is the part that handles the future: it is a template applied to files created later, so new archives automatically grant the <code>logadmins</code> group read and write without anyone re-running setfacl. Read the result with <code>getfacl</code>, and remember the mask caps the effective rights of every named entry.</p></div>

<h2 id="wt-10" class="pp-h2">Task 10: Extend log storage online</h2>

<div class="pp-domain">Domain 4 + Domain 5</div>

<div class="pp-deepdive"><div class="pp-deepdive-label">// deep dive</div><p>Growing storage while the system stays online is one of the strongest arguments for LVM, and it is a two-layer operation. The logical volume is the container; the filesystem is what lives inside it. Making more room means enlarging both, in order.</p><p><code>lvextend -L +1G</code> hands another gigabyte of free extents from the volume group to <code>lv&#95;logs</code>. At that instant the block device is bigger, but the filesystem still believes it is the old size, so the extra space is unusable until you grow the filesystem into it.</p><p><code>xfs&#95;growfs</code> does that second step, and three details matter. It takes the <b>mount point</b>, not the device path. It works fully online, with the filesystem mounted and in use, so there is no downtime. And XFS only ever grows: it cannot be shrunk, which is a deliberate design tradeoff, so plan sizes with that in mind. You can collapse both steps into <code>lvextend -r</code>, which resizes the filesystem automatically, but doing them separately makes each layer visible.</p></div>

<p><b>Goal:</b> Grow <code>lv&#95;logs</code> by 1 GiB with no unmount and no data loss.</p><h4 class="pp-step">Step 10.1: Extend the LV, then grow the filesystem</h4><div class="pp-code"><div class="pp-code-head"><div class="pp-code-dots"><div class="pp-code-dot" style="background:#ff5f57"></div><div class="pp-code-dot" style="background:#febc2e"></div><div class="pp-code-dot" style="background:#28c840"></div></div><div class="pp-code-lang">bash</div><button class="pp-code-copy" onclick="navigator.clipboard.writeText(this.closest('.pp-code').querySelector('pre').textContent);this.textContent='copied!';setTimeout(()=>this.textContent='copy',1500)">copy</button></div><div class="pp-code-body"><pre>{`lvextend -L +1G /dev/vg_logs/lv_logs\nxfs_growfs /var/log/remote\ndf -h /var/log/remote`}</pre></div></div><p>Order matters: extend the logical volume first, then grow the filesystem into the new space. <code>xfs&#95;growfs</code> takes the mount point, not the device, and works online.
