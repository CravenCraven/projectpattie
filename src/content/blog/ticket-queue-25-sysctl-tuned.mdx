<p>dbadmin1 is tuning the DB tier and hands you two exact numbers: raise <code>net.core.somaxconn</code>, the TCP listen queue, to 4096, and pin <code>vm.swappiness</code> at 10, the value from the emergency-swap ticket, this time confirming it actually survives a reboot. Both belong in <code>/etc/sysctl.d/</code>. Then switch the box to the <code>throughput-performance</code> tuned profile so the kernel favors sustained throughput, and show what that profile quietly changes underneath.</p>

<p>Two things trip people. A value set with <code>sysctl -w</code> is live immediately but gone at the next reboot, so persistence means a file, not a flag. And a sysctl drop-in and a tuned profile can both reach for the same knob, so when they disagree you have to know the drop-in wins.</p>

<p>Common profiles: <code>balanced</code> is the default, <code>throughput-performance</code> is for servers under sustained load, <code>latency-performance</code> for low latency, and <code>virtual-guest</code> for VMs.</p>

<h2 id="persist" class="pp-h2">Set persistent values in sysctl.d</h2>

<p>Write a drop-in rather than editing <code>/etc/sysctl.conf</code>, which is effectively deprecated. The <code>99-</code> prefix makes the file load last so it wins over earlier defaults. Then apply without a reboot.</p>

<div class="pp-code"><div class="pp-code-head"><div class="pp-code-dots"><div class="pp-code-dot"></div><div class="pp-code-dot"></div><div class="pp-code-dot"></div></div><div class="pp-code-lang">bash</div><button class="pp-code-copy" onclick="navigator.clipboard.writeText(this.closest('.pp-code').querySelector('pre').textContent);this.textContent='copied!';setTimeout(()=>this.textContent='copy',1500)">copy</button></div><div class="pp-code-body"><pre>{`sudo tee /etc/sysctl.d/99-server1-db-tuning.conf << 'EOF'\n# DB tier tuning\nvm.swappiness = 10\nnet.core.somaxconn = 4096\nEOF\n\nsudo sysctl --system    # shows which file each value came from\nsysctl net.core.somaxconn vm.swappiness`}</pre></div></div>

<h2 id="tuned" class="pp-h2">Apply and verify a tuned profile</h2>

<p>Switching a profile is persistent by design, stored in <code>/etc/tuned/active_profile</code> and reapplied at boot, so there is no separate persistence step. <code>verify</code> confirms the live system still matches the profile.</p>

<div class="pp-code"><div class="pp-code-head"><div class="pp-code-dots"><div class="pp-code-dot"></div><div class="pp-code-dot"></div><div class="pp-code-dot"></div></div><div class="pp-code-lang">bash</div><button class="pp-code-copy" onclick="navigator.clipboard.writeText(this.closest('.pp-code').querySelector('pre').textContent);this.textContent='copied!';setTimeout(()=>this.textContent='copy',1500)">copy</button></div><div class="pp-code-body"><pre>{`tuned-adm list\nsudo tuned-adm profile throughput-performance\ntuned-adm active\nsudo tuned-adm verify\n\n# see what the profile actually sets\ncat /usr/lib/tuned/throughput-performance/tuned.conf`}</pre></div></div>

<h2 id="collision" class="pp-h2">When a drop-in and tuned collide</h2>

<p>If <code>tuned-adm verify</code> ever fails, something is overriding the profile, and it is usually one of your own <code>/etc/sysctl.d/</code> files. For sysctl values, the drop-in wins over tuned. Decide which value you actually want and keep them consistent.</p>
