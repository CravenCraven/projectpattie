<p>Last ticket in the queue, and it is the calm one: a low-priority research task. Procurement is weighing storage options for the next refresh, and dbadmin1 wants a real proof of concept for Stratis, the managed pool-and-filesystem layer Red Hat pitches as a more modern take than LVM plus XFS. Build a pool on the spare partition <code>/dev/sdb3</code>, put a filesystem on it at <code>/srv/stratis_test</code>, snapshot it, prove the snapshot survives after you wreck the source, and write up how it differs from the LVM workflow. The production <code>dbvg/dblv</code> from earlier in the queue stays untouched.</p>

<p>Stratis is opinionated where LVM handed you the wheel, and two differences carry the ticket. The filesystem is always XFS, created and grown for you, so there is no <code>mkfs</code> and no <code>lvextend</code> plus <code>xfs_growfs</code> dance. And it is daemon-driven, which means the fstab mount has to wait for <code>stratisd</code> or the boot fails outright.</p>

<h2 id="concept-review" class="pp-h2">Concept review. Stratis versus LVM.</h2>

<p>The mental model maps cleanly onto LVM. A Stratis pool is like a volume group. A Stratis filesystem is like a logical volume, except it is XFS, thin-provisioned, and grown automatically, so there is no separate mkfs and no <code>lvextend</code> plus <code>xfs_growfs</code> dance. Adding a disk is <code>stratis pool add-data</code> instead of <code>vgextend</code>, and snapshots are <code>stratis filesystem snapshot</code> instead of <code>lvcreate -s</code>. The big difference is that Stratis runs a daemon, <code>stratisd</code>, rather than being kernel-only like LVM.</p>

<h2 id="pool" class="pp-h2">Build a pool and a filesystem</h2>

<p>Install the daemon and CLI, wipe any old signatures off the spare partition, then create the pool and a filesystem in it. Stratis filesystems appear under <code>/dev/stratis/POOL/FS</code>.</p>

<div class="pp-code"><div class="pp-code-head"><div class="pp-code-dots"><div class="pp-code-dot"></div><div class="pp-code-dot"></div><div class="pp-code-dot"></div></div><div class="pp-code-lang">bash</div><button class="pp-code-copy" onclick="navigator.clipboard.writeText(this.closest('.pp-code').querySelector('pre').textContent);this.textContent='copied!';setTimeout(()=>this.textContent='copy',1500)">copy</button></div><div class="pp-code-body"><pre>{`sudo dnf install -y stratisd stratis-cli\nsudo systemctl enable --now stratisd\n\nsudo wipefs -a /dev/sdb3          # removes old signatures, destroys data on it\nsudo stratis pool create poc_pool /dev/sdb3\nsudo stratis pool list\n\nsudo stratis filesystem create poc_pool data\nsudo mkdir -p /srv/stratis_test\nsudo mount /dev/stratis/poc_pool/data /srv/stratis_test\ndf -h /srv/stratis_test`}</pre></div></div>

<h2 id="persist" class="pp-h2">Persist it, and the flag that matters</h2>

<p>The fstab entry uses the UUID and the filesystem type <code>xfs</code>, not <code>stratis</code>. The critical option is <code>x-systemd.requires=stratisd.service</code>, which tells systemd to wait for the daemon before mounting. Without it, boot tries to mount a device that does not exist yet and fails.</p>

<div class="pp-code"><div class="pp-code-head"><div class="pp-code-dots"><div class="pp-code-dot"></div><div class="pp-code-dot"></div><div class="pp-code-dot"></div></div><div class="pp-code-lang">bash</div><button class="pp-code-copy" onclick="navigator.clipboard.writeText(this.closest('.pp-code').querySelector('pre').textContent);this.textContent='copied!';setTimeout(()=>this.textContent='copy',1500)">copy</button></div><div class="pp-code-body"><pre>{`UUID=$(sudo blkid -s UUID -o value /dev/stratis/poc_pool/data)\necho "UUID=$UUID /srv/stratis_test xfs defaults,x-systemd.requires=stratisd.service 0 0" | sudo tee -a /etc/fstab\n\nsudo umount /srv/stratis_test\nsudo mount -a\nmount | grep stratis_test`}</pre></div></div>
