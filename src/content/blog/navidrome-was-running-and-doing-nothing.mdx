<h2 class="pp-h2" id="start">How this started</h2>

<p><a href="/blog/my-daily-driver-was-talking-to-the-wrong-cluster/">The last post</a> ended with two Navidrome settings that had been quietly doing nothing, and my music still sitting on my Mac instead of the Dell. Thursday night I opened the checklist to block 4 and gave it 45 minutes.</p>

<p>Música is the music library tile in Laboratório Brasil. It is also the first tile I want to put on the internet, so before anyone else touches it I wanted to know it works. Not that the pod is green. That I can press play on a bossa nova album and hear the whole song.</p>

<p>It took a lot longer than 45 minutes.</p>

<p><code>get</code> tells you what Kubernetes thinks. <code>logs</code> tells you what the app thinks. Kubernetes thought Navidrome was fine. Navidrome was telling me three things were not.</p>

<ul>
  <li><code>Periodic scan is DISABLED</code>. I had set a 3am daily scan in the manifest. Navidrome did not know about it.</li>
  <li>The scan finished in 2.8 milliseconds. Nothing scans a real music library that fast. The library was empty.</li>
  <li><code>no admin users yet</code>. In Navidrome, whoever logs in first becomes the admin. The ingress was already live on my home network. That is a race I wanted to win.</li>
</ul>

<h2 class="pp-h2" id="settings">Two settings that did nothing</h2>

<p>Here is what was in <code>clusters/staging/brasil/navidrome.yaml</code>:</p>

<div class="pp-code"><div class="pp-code-head"><div class="pp-code-dots"><div class="pp-code-dot"></div><div class="pp-code-dot"></div><div class="pp-code-dot"></div></div><div class="pp-code-lang">yaml</div><button class="pp-code-copy" onclick="navigator.clipboard.writeText(this.closest('.pp-code').querySelector('pre').textContent);this.textContent='copied!';setTimeout(()=>this.textContent='copy',1500)">copy</button></div><div class="pp-code-body"><pre>{`- name: ND_SCANSCHEDULE\n  value: "0 3 * * *"\n- name: ND_ENABLESTARTUPSCAN\n  value: "true"`}</pre></div></div>

<p>Navidrome renamed these at some point. The current names are <code>ND_SCANNER_SCHEDULE</code> and <code>ND_SCANNER_SCANONSTARTUP</code>. An app does not throw an error on an environment variable it does not recognize. It just skips it. The manifest looked right. The pod was healthy. The scan schedule did not exist.</p>

<p>The startup scan was sneakier. It did run. But only because it is on by default. My setting was being ignored the same way, and the default happened to match what I wanted. I fixed it anyway. I would rather the config say what it means than get lucky.</p>

<p><code>DISABLED</code> became <code>Scheduling periodic scan</code>. Fixed, and I can point at the line that proves it.</p>

<p>Two things came with it.</p>

<p>My port-forward died. It was attached to the old pod, and the old pod was gone. Port-forward picks one pod when it starts and stays with it. Hold onto that, it comes back later.</p>

<p>And 3am is not 3am. The log timestamps end in <code>Z</code>, which means UTC. The container runs on UTC, so <code>0 3 * * *</code> is 11pm in Miami. A library scan at 11pm does not bother me. A backup job would.</p>

<h3 id="volume">Which volume, and where does it live</h3>

<p>Navidrome has two volumes:</p>

<p>The Dell, under <code>/var/lib/rancher</code>. Which is owned by root.</p>

<h3 id="rsync">rsync and sudo</h3>

<p>My user on the Dell cannot write there. So I tried a dry run that runs rsync with sudo on the far end:</p>

<div class="pp-code"><div class="pp-code-head"><div class="pp-code-dots"><div class="pp-code-dot"></div><div class="pp-code-dot"></div><div class="pp-code-dot"></div></div><div class="pp-code-lang">bash</div><button class="pp-code-copy" onclick="navigator.clipboard.writeText(this.closest('.pp-code').querySelector('pre').textContent);this.textContent='copied!';setTimeout(()=>this.textContent='copy',1500)">copy</button></div><div class="pp-code-body"><pre>{`rsync -avhn --rsync-path="sudo rsync" ~/Music/brasil/ dell:/var/lib/rancher/k3s/storage/<pv-folder>/\n#    -> sudo: a terminal is required to read the password; either use ssh's -t option or configure an askpass helper\n#    -> sudo: a password is required\n#    -> rsync error: unexpected end of file`}</pre></div></div>

<p>I have seen this exact error before. It is the same one from getting the kubeconfig off the server. rsync runs over SSH with no terminal, so sudo has nowhere to ask for my password.</p>

<p>One fix is a sudoers rule that lets my user run rsync with no password. That is a real security decision and I did not want to make it at 8:30 at night. So I went with two hops.</p>

<div class="pp-code"><div class="pp-code-head"><div class="pp-code-dots"><div class="pp-code-dot"></div><div class="pp-code-dot"></div><div class="pp-code-dot"></div></div><div class="pp-code-lang">bash</div><button class="pp-code-copy" onclick="navigator.clipboard.writeText(this.closest('.pp-code').querySelector('pre').textContent);this.textContent='copied!';setTimeout(()=>this.textContent='copy',1500)">copy</button></div><div class="pp-code-body"><pre>{`# daily driver to my home folder on the Dell, which I own\nrsync -avh ~/Music/brasil/ dell:~/navidrome-upload/\n#    -> sent 735M bytes  received 1276 bytes  33584k bytes/sec\n\n# then on the Dell, where sudo has a terminal\nssh dell\nsudo rsync -avh ~/navidrome-upload/ /var/lib/rancher/k3s/storage/<pv-folder>/\nsudo ls /var/lib/rancher/k3s/storage/<pv-folder>/\nrm -rf ~/navidrome-upload\nexit`}</pre></div></div>

<div class="pp-note"><strong>worth knowing:</strong> the slash at the end of <code>~/Music/brasil/</code> matters. With it, rsync copies what is inside the folder. Without it, rsync copies the folder itself, and the library ends up at <code>/music/brasil/Artist/...</code>. That is how you end up with folders inside folders you did not ask for.</div>

<h2 class="pp-h2" id="testing">Testing it</h2>

<p>Four checks. Each one proves something the one before it does not.</p>

<p><strong>Can I reach it.</strong> I started the port-forward again on my Mac and opened <code>localhost:4533</code>. The terminal immediately filled up with this:</p>

<div class="pp-code"><div class="pp-code-head"><div class="pp-code-dots"><div class="pp-code-dot"></div><div class="pp-code-dot"></div><div class="pp-code-dot"></div></div><div class="pp-code-lang">text</div><button class="pp-code-copy" onclick="navigator.clipboard.writeText(this.closest('.pp-code').querySelector('pre').textContent);this.textContent='copied!';setTimeout(()=>this.textContent='copy',1500)">copy</button></div><div class="pp-code-body"><pre>{`E0924 20:40:10.820561   87651 portforward.go:489] "Unhandled Error" err="error copying from remote stream to local connection: ... write: broken pipe"`}</pre></div></div>

<p>It looked bad. It was not. The browser closes connections early all the time, when you click away or it cancels an image it does not need anymore. Port-forward logs every one of them. The page was working fine.</p>

<p><strong>Did it find the music.</strong> Astrud Gilberto, <em>The Bossa Nova Queen</em>, 12 songs, cover art and all. All four albums were there. The files were in the right volume and the scanner found them.</p>

<p><strong>Does it play.</strong> I played a song all the way through. A library that lists albums and cannot stream them is a catalog. Playback proves the whole path works, from the browser through the forward to the pod to the disk on the Dell and back.</p>

<p><strong>Does it survive a restart.</strong> This is the one I care about most. If the music or the database lived inside the container, a restart would wipe them. I ran this from my daily driver, which after last week can actually talk to the cluster:</p>

<div class="pp-code"><div class="pp-code-head"><div class="pp-code-dots"><div class="pp-code-dot"></div><div class="pp-code-dot"></div><div class="pp-code-dot"></div></div><div class="pp-code-lang">bash</div><button class="pp-code-copy" onclick="navigator.clipboard.writeText(this.closest('.pp-code').querySelector('pre').textContent);this.textContent='copied!';setTimeout(()=>this.textContent='copy',1500)">copy</button></div><div class="pp-code-body"><pre>{`kubectl -n brasil rollout restart deploy/navidrome\n#    -> deployment.apps/navidrome restarted\n\nkubectl -n brasil get pods | grep navidrome\n#    -> navidrome-7c4d684dd9-5jfnv   1/1   Running   0   10s`}</pre></div></div>

<p>New pod, 10 seconds old. I refreshed the browser.</p>

<div class="pp-code"><div class="pp-code-head"><div class="pp-code-dots"><div class="pp-code-dot"></div><div class="pp-code-dot"></div><div class="pp-code-dot"></div></div><div class="pp-code-lang">text</div><button class="pp-code-copy" onclick="navigator.clipboard.writeText(this.closest('.pp-code').querySelector('pre').textContent);this.textContent='copied!';setTimeout(()=>this.textContent='copy',1500)">copy</button></div><div class="pp-code-body"><pre>{`This site can't be reached\nlocalhost refused to connect.\nERR_CONNECTION_REFUSED`}</pre></div></div>

<p>For a second I thought the library was gone. Then I remembered what happened an hour earlier. The port-forward was attached to the old pod. The old pod was gone, so nothing was listening on 4533 anymore. I stopped the forward, started it again, and refreshed.</p>

<p>Everything was there. The albums, my login, all of it.</p>

<p>That is the whole point of the test. The music lives on <code>navidrome-music</code>, the database lives on <code>navidrome-data</code>, and the container can die whenever it wants.</p>

<p>I hit enough port-forward errors that night to fill a post of their own, so <a href="/blog/five-ways-i-broke-port-forward/">they got one</a>.</p>
