<h1 class="pp-title">Deploy a Secure Web Server <em>with Persistent Storage</em></h1>

<p class="pp-subtitle">An exam-level RHEL 9 capstone you attempt first, then a deep-dive walkthrough.</p>

<div class="pp-series-badge">RHCSA EX200 Exam · Project 1 of 10</div>

<div class="pp-tags"><span class="pp-tag">#rhcsa</span><span class="pp-tag">#ex200</span><span class="pp-tag">#rhel9</span><span class="pp-tag">#lvm</span><span class="pp-tag">#selinux</span><span class="pp-tag">#nginx</span><span class="pp-tag">#systemd</span><span class="pp-tag">#podman</span><span class="pp-tag">#firewalld</span><span class="pp-tag">#exam</span></div>

<div class="pp-brief"><p><span class="c-light">Scenario:</span> You are a sysadmin setting up <code>webserver1.lab.example.com</code> as a production-ready internal web server. It needs dedicated LVM storage, a service account, hardened SSH, an automated backup script, nginx serving a custom page, a Podman monitoring container that starts at boot, and NTP configured correctly.</p><p><span class="c-light">Domains Covered:</span> All 6 (D1 through D6)</p><p><span class="c-light">Estimated Time:</span> 90–120 minutes</p><p><span class="c-light">Difficulty:</span> Exam-level</p><p><span class="c-light">Rule:</span> Every configuration must survive a reboot. Verify after rebooting.</p></div>

<div class="pp-note"><strong>note:</strong> You need a clean RHEL 9 VM with root access, one extra unpartitioned disk at <code>/dev/sdb</code> for Task 1, and internet access. No Git repository is involved. <code>dnf</code> pulls <code>nginx</code> and <code>autofs</code> from your software repositories (a Red Hat subscription, or Rocky/AlmaLinux 9), and <code>podman pull</code> fetches one public image (<code>ubi9/ubi-minimal</code>, no login). Task 11 points autofs at a fictional NFS host, so <code>ls /mnt/content</code> stays empty unless you stand up a matching export. That is expected.</div>

<div class="pp-part" id="p1">Part 1: The Exam<small>Attempt every task on your own first. Every configuration must survive a reboot.</small></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 1: Partition and mount web storage</h3><div class="pp-domain">Domain 4 + Domain 5</div><p>Create a 2 GiB LVM Logical Volume named <code>lv_webdata</code> inside a new Volume Group <code>vg_web</code> using <code>/dev/sdb</code>. Format it as XFS. Mount it persistently at <code>/var/www/html</code> using its UUID in <code>/etc/fstab</code>.</p></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 2: Create the web service account</h3><div class="pp-domain">Domain 1</div><p>Create the group <code>webteam</code> with GID 6000. Create user <code>webadmin</code> with UID 6001, primary group <code>webteam</code>, and no login shell (<code>/sbin/nologin</code>). Set ownership of <code>/var/www/html</code> to <code>root:webteam</code>. Set the setGID bit so all new files created inside inherit the <code>webteam</code> group. Permissions should be <code>2775</code>.</p></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 3: Deploy nginx and configure the firewall</h3><div class="pp-domain">Domain 6</div><p>Install the <code>nginx</code> package. Enable and start the service. Configure <code>firewalld</code> to permanently allow HTTP and HTTPS traffic. <div class="pp-exam-task"><h3 class="pp-h3">Task 4: Set the correct SELinux context</h3><div class="pp-domain">Domain 5</div><p>Apply the SELinux file context <code>httpd_sys_content_t</code> to <code>/var/www/html</code> and all files inside it. Make the context persistent using <code>semanage fcontext</code> and apply it with <code>restorecon</code>. Verify nginx can serve the page with <code>curl localhost</code>.</p></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 5: Harden SSH access</h3><div class="pp-domain">Domain 3 + Domain 6</div><p>Edit <code>/etc/ssh/sshd_config</code> to:</p><ul><li>Disable root login (<code>PermitRootLogin no</code>)</li><li>Disable password authentication (<code>PasswordAuthentication no</code>)</li><li>Allow only users in the <code>webteam</code> group (<code>AllowGroups webteam</code>)</li></ul><p>Add your current user to the <code>webteam</code> group before restarting sshd to avoid locking yourself out. Restart the <code>sshd</code> service.</p></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 6: Write an automated backup script</h3><div class="pp-domain">Domain 2</div><p>Create an executable script at <code>/usr/local/bin/web_backup.sh</code> that:</p><ul><li>Takes no arguments</li><li>Creates a <code>.tar.gz</code> archive of <code>/var/www/html</code></li><li>Names the archive <code>web_YYYYMMDD.tar.gz</code> using the current date</li><li>Saves it to <code>/backups/</code> (create the directory if it does not exist)</li><li>Prints <code>Backup created: /backups/web_YYYYMMDD.tar.gz</code> on success</li><li>Prints <code>ERROR: Backup failed</code> and exits with code 1 on failure</li></ul></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 7: Schedule the backup with cron and a systemd timer</h3><div class="pp-domain">Domain 6</div><ol><li>Add a root crontab entry to run <code>/usr/local/bin/web_backup.sh</code> every night at 2:00 AM</li><li>Create a systemd service unit at <code>/etc/systemd/system/web-backup.service</code> and a timer unit at <code>/etc/systemd/system/web-backup.timer</code> that runs the backup every 6 hours. Enable and start the timer.</li></ol></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 8: Configure NTP and timezone</h3><div class="pp-domain">Domain 6</div><p>Set the system timezone to <code>America/New_York</code>. Configure <code>chronyd</code> to use <code>time.cloudflare.com iburst</code> as its NTP source. Remove or comment out any existing pool or server lines. Restart chronyd and verify synchronization is active.</p></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 9: Run a Podman monitoring container</h3><div class="pp-domain">Domain 6</div><p>As root, pull <code>registry.access.redhat.com/ubi9/ubi-minimal:latest</code>. Run a detached container named <code>webmon</code> that:</p><ul><li>Mounts <code>/var/log/nginx</code> on the host to <code>/logs</code> inside the container (use <code>:Z</code> for SELinux)</li><li>Runs <code>sleep infinity</code></li></ul><p>Generate a systemd unit file with <code>podman generate systemd</code>, place it in <code>/etc/systemd/system/</code>, enable it, and confirm it starts after a reboot.</p></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 10: Make the journal persistent and set boot target</h3><div class="pp-domain">Domain 3</div><p>Configure <code>/etc/systemd/journald.conf</code> with <code>Storage=persistent</code> and <code>SystemMaxUse=300M</code>. Create <code>/var/log/journal/</code> to activate persistence. Set the default systemd boot target to <code>multi-user.target</code>. Restart journald.</p></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 11: Configure autofs for shared content</h3><div class="pp-domain">Domain 5</div><p>Configure autofs to automatically mount <code>fileserver.lab.example.com:/exports/content</code> at <code>/mnt/content</code> when accessed. Use an indirect map. Enable and start the autofs service.</p></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 12: Reboot and verify everything</h3><div class="pp-domain">All Domains</div><p>Reboot the system and confirm every configuration survived. Run through the verification checklist in the Outcomes section below.</p></div>

<h2 id="wt-01" class="pp-h2">Task 1: Partition and Mount Web Storage</h2>

<div class="pp-domain">Domain 4 + Domain 5</div>

<div class="pp-deepdive"><div class="pp-deepdive-label">// deep dive</div><p>Traditional disk partitions are fixed at creation. Size <code>/var/www/html</code> at 2&nbsp;GB today and need 20&nbsp;GB next quarter, and a raw partition forces a backup-repartition-restore cycle. <b>LVM</b> (Logical Volume Manager) inserts a layer of indirection between the physical disk and the filesystem that makes storage elastic, which is exactly why the exam leans on it.</p>
<p>The stack has three tiers. A <b>physical volume</b> (PV) is a disk or partition handed to LVM with <code>pvcreate</code>. One or more PVs are pooled into a <b>volume group</b> (VG) with <code>vgcreate</code>, think of the VG as a single allocatable capacity pool. From that pool you carve <b>logical volumes</b> (LVs) with <code>lvcreate</code>; an LV behaves like a partition but can be grown, and in some cases shrunk or moved, while mounted. The kernel exposes each LV through device-mapper at <code>/dev/mapper/vg_web-lv_webdata</code>, with a convenience symlink at <code>/dev/vg_web/lv_webdata</code>. Capacity is tracked in fixed-size <i>physical extents</i> (4&nbsp;MiB by default), which is why volumes always round to extent boundaries.</p>
<p><b>XFS</b> is the RHEL&nbsp;9 default filesystem, a high-performance journaling filesystem built for large volumes and heavy parallel I/O. One exam-critical quirk: XFS can be <i>grown</i> online with <code>xfs_growfs</code> but can <b>never be shrunk</b>. If a task ever says &ldquo;reduce the filesystem,&rdquo; that is ext4 territory, not XFS.</p>
<p>Persistence lives in <code>/etc/fstab</code>, which systemd reads at every boot to assemble the mount tree. The golden rule is to mount by <b>UUID</b>, never by device path: kernel names like <code>/dev/sdb</code> are assigned in device-discovery order and can shift when disks are added or reordered, whereas a filesystem UUID is written into the superblock and is stable for the life of the filesystem. The six fstab fields are device, mount point, type, options, dump, and pass. <code>defaults 0 0</code> means standard options, no <code>dump</code>-based backup, and no boot-time <code>fsck</code>, XFS performs its consistency checks online, so the pass field is <code>0</code>.</p>
<p>The cost of an fstab mistake is severe and is a classic way to fail the exam: a single bad entry can drop the system into emergency mode on the next boot. That is why you always run <code>mount -a</code> immediately after editing, it mounts everything declared in fstab and surfaces syntax or UUID errors <i>now</i>, while they are trivial to fix, rather than at the reboot when they are not.</p></div>

<h2 id="wt-02" class="pp-h2">Task 2: Create the Web Service Account</h2>

<div class="pp-domain">Domain 1</div>

<div class="pp-deepdive"><div class="pp-deepdive-label">// deep dive</div><p>Linux identity is numeric. Every user has a <b>UID</b> and every group a <b>GID</b>; the names you see are a convenience layer resolved through <code>/etc/passwd</code> and <code>/etc/group</code>. By convention, UIDs and GIDs below 1000 are reserved for the system and services, while regular human accounts start at 1000. Choosing 6000/6001 here deliberately places this service identity in the &ldquo;service&rdquo; range, well clear of real users.</p>
<p>A user has exactly one <b>primary group</b> (the GID recorded in <code>/etc/passwd</code>, applied to files they create) and any number of <b>supplementary groups</b>. <code>useradd -g webteam</code> sets the primary group explicitly; omit it and <code>useradd</code> helpfully creates a brand-new private group named after the user and ignores your intended GID scheme. The login shell matters too: <code>/sbin/nologin</code> gives the account no interactive shell, so it can own files and run services but cannot be logged into, the correct posture for a service account that should never have a human at a prompt.</p>
<p>Standard permissions are the familiar three triads, owner, group, other, each carrying read (4), write (2), and execute (1). On top of those sit three <b>special bits</b>, expressed as a leading fourth octal digit: setuid (4), setgid (2), and the sticky bit (1). The task uses <b>setgid on a directory</b>, which is the conceptual heart of this exercise. A setgid directory forces every file and subdirectory created inside it to inherit the <i>directory&rsquo;s</i> group rather than the creating user&rsquo;s primary group.</p>
<p>That is why <code>2775</code> is precise, not arbitrary. The leading <code>2</code> is setgid, guaranteeing new content stays owned by <code>webteam</code> no matter who writes it. <code>7</code> for owner and <code>7</code> for group give the team full read/write/execute. The final <code>5</code>, read and execute for others, is what lets the nginx worker process, which runs as an unprivileged user outside <code>webteam</code>, traverse the directory and read the files it serves. Drop that to <code>2770</code> and nginx returns 403s. Set ownership with <code>chown</code> <i>before</i> <code>chmod</code>, because the setgid bit binds to whatever group owns the directory at the moment it is set.</p></div>

<h2 id="wt-04" class="pp-h2">Task 4: Set the Correct SELinux Context</h2>

<div class="pp-domain">Domain 5</div>

<div class="pp-deepdive"><div class="pp-deepdive-label">// deep dive</div><p><b>SELinux</b> is mandatory access control layered on top of ordinary Unix permissions. Even when the file mode says &ldquo;allowed,&rdquo; SELinux can still deny the access if the policy disagrees, which is precisely why a perfectly readable file can still produce a 403 from nginx. The mechanism is <b>type enforcement</b>: every process runs in a <i>domain</i> and every file carries a <i>type</i>, and the policy defines which domains may touch which types.</p>
<p>A context has four colon-separated fields, SELinux user, role, <b>type</b>, and level, but for file labeling the type is the field that decides everything. Web content must carry <code>httpd_sys_content_t</code>, because the web server domain (<code>httpd_t</code>, which nginx shares on RHEL) is permitted to read exactly that type. The default policy already labels <code>/usr/share/nginx/html</code> and <code>/var/www</code> correctly; the moment you serve content from a freshly mounted LVM volume, that new filesystem has no such labeling and you must establish it yourself.</p>
<p>There are two ways to set a context, and choosing correctly is the exam point. <code>chcon</code> changes the label on disk immediately but does <b>not</b> record it in policy, so the next filesystem relabel, or a stray <code>restorecon</code>, silently reverts it. <code>semanage fcontext -a</code> writes a <i>rule</i> into the local policy describing what the label <i>should</i> be, making the change durable; <code>restorecon</code> then reads that policy and applies the correct label to files on disk. The persistent, correct workflow is always <code>semanage fcontext</code> followed by <code>restorecon</code>.</p>
<p>The regular-expression suffix <code>(/.\*)?</code> is essential and frequently forgotten. It means &ldquo;this directory <i>and</i> everything beneath it.&rdquo; Without it the rule labels only the directory node and leaves the files inside unlabeled, which produces the maddening symptom of a correctly contexted directory that still cannot be served. Finally, verify with <code>getenforce</code>: if SELinux is <code>Permissive</code>, denials are logged but not enforced, so a working <code>curl</code> proves nothing, the misconfiguration is waiting to bite the instant the system returns to <code>Enforcing</code>.</p></div>

<h2 id="wt-05" class="pp-h2">Task 5: Harden SSH Access</h2>

<div class="pp-domain">Domain 3 + Domain 6</div>

<div class="pp-deepdive"><div class="pp-deepdive-label">// deep dive</div><p>Hardening SSH is where a careless command turns into a locked-out host, so the order of operations is the lesson. Three directives in <code>/etc/ssh/sshd_config</code> do the work. <code>PermitRootLogin no</code> blocks direct root authentication, forcing administrators to log in as a normal user and escalate, which preserves an audit trail and removes the single most attacked username on the internet. <code>PasswordAuthentication no</code> disables password logins entirely, defeating brute-force and credential-stuffing attacks by requiring cryptographic keys. <code>AllowGroups webteam</code> is an allow-list: only members of <code>webteam</code> may authenticate at all, regardless of other settings.</p>

<p>The professional safeguard is <code>sshd -t</code>, which parses the configuration and validates syntax without touching the running daemon. <h2 id="wt-06" class="pp-h2">Task 6: Write an Automated Backup Script</h2>

<div class="pp-domain">Domain 2</div>

<div class="pp-deepdive"><div class="pp-deepdive-label">// deep dive</div><p>This task is a compact lesson in defensive shell scripting. The <b>shebang</b> <code>#!/bin/bash</code> on line one tells the kernel which interpreter to use; without it the script may run under whatever shell happens to invoke it, with subtly different behavior. <b>Command substitution</b>, <code>$(date +%Y%m%d)</code>, captures the output of a command into a variable, here producing a dated filename like <code>web_20260420.tar.gz</code> so each run is uniquely named rather than overwriting the last.</p>
<p>The script&rsquo;s correctness hinges on <b>checking the exit status</b>. Every command returns a status code: <code>0</code> for success, non-zero for failure. Wrapping <code>tar</code> in <code>if tar &hellip;; then</code> branches on that status, so the script reports &ldquo;Backup created&rdquo; only when the archive truly succeeded and exits <code>1</code> on failure, a non-zero exit is what lets schedulers and monitoring detect that the job broke. <code>tar -czf</code> means create, gzip-compress, and write to the named file; the <code>2&gt;/dev/null</code> discards <code>tar</code>&rsquo;s harmless &ldquo;removing leading /&rdquo; notice on stderr.</p>
<p>A subtle but important detail is the <b>quoted heredoc</b>, <code>&lt;&lt;'EOF'</code>. <h2 id="wt-07" class="pp-h2">Task 7: Schedule the Backup</h2>

<div class="pp-domain">Domain 6</div>

<div class="pp-deepdive"><div class="pp-deepdive-label">// deep dive</div><p>Scheduling the same job two ways is deliberate: the exam wants proof you can drive both the classic and the modern scheduler. <b>cron</b> is the traditional time-based job runner. A crontab line has five time fields, minute, hour, day-of-month, month, day-of-week, followed by the command. <code>0 2 \* \* \*</code> reads as &ldquo;minute 0 of hour 2, every day, every month, every weekday,&rdquo; i.e. 2:00&nbsp;AM nightly. The most common error is field-order confusion; <code>2 \* \* \* \*</code> would instead run at two minutes past <i>every</i> hour.</p>
<p>The systemd approach splits the work across two units. A <b>service</b> unit defines <i>what</i> to run; here <code>Type=oneshot</code> is correct because the script runs to completion and exits, as opposed to <code>Type=simple</code> for long-lived daemons. A <b>timer</b> unit defines <i>when</i>, and is bound to the service it triggers. This timer uses <i>monotonic</i> triggers: <code>OnBootSec=10min</code> fires ten minutes after boot, and <code>OnUnitActiveSec=6h</code> fires every six hours after the previous activation. (The alternative, <code>OnCalendar=</code>, expresses wall-clock schedules like cron.)</p>
<p>Two operational rules trip people up. First, after writing or editing any unit file you must run <code>systemctl daemon-reload</code> so systemd re-reads its configuration, skip it and systemd behaves as though the unit does not exist. Second, you enable and start the <b>timer</b>, not the service: enabling the service would run the backup once at enable time and never again, while enabling the timer is what installs the recurring schedule. Confirm the result with <code>systemctl list-timers</code>, which shows the next scheduled firing.</p></div>

<h2 id="wt-08" class="pp-h2">Task 8: Configure NTP and Timezone</h2>

<div class="pp-domain">Domain 6</div>

<div class="pp-deepdive"><div class="pp-deepdive-label">// deep dive</div><p>Accurate time is infrastructure, not housekeeping. Kerberos authentication rejects requests whose clocks skew more than a few minutes, TLS certificate validation depends on the current time, and correlating logs across machines is impossible if their clocks disagree. RHEL&nbsp;9 keeps time with <b>chrony</b>, whose daemon <code>chronyd</code> disciplines the system clock against network time sources defined in <code>/etc/chrony.conf</code>.</p>
<p>That file distinguishes a <code>pool</code> directive, a DNS name that resolves to many rotating servers, from a <code>server</code> directive naming one specific source. The <code>iburst</code> option tells chrony to send a rapid initial burst of packets on startup so it can lock on in seconds rather than minutes.</p>
<p>Verification is its own skill. <code>chronyc sources</code> lists each source with a status glyph in the first column: <code>^\*</code> marks the currently selected, synchronized source; <code>^+</code> an acceptable alternate; and <code>^?</code> a source not yet reachable. Seeing <code>^?</code> right after a restart is normal, wait and re-check. Separately, <code>timedatectl</code> shows the timezone and whether NTP synchronization is active; the timezone itself is a property of the system set with <code>timedatectl set-timezone</code>, independent of the clock-sync source.</p></div>

<h2 id="wt-10" class="pp-h2">Task 10: Make the Journal Persistent and Set Boot Target</h2>

<div class="pp-domain">Domain 3</div>

<div class="pp-deepdive"><div class="pp-deepdive-label">// deep dive</div><p>The systemd <b>journal</b> (<code>systemd-journald</code>) is the central, structured log store for the whole system. By default on many installs it is <i>volatile</i>: logs live in <code>/run/log/journal</code>, which is a tmpfs in RAM, so every reboot wipes the history, fine for a throwaway box, useless for diagnosing why a server crashed last night. Switching to <i>persistent</i> storage keeps logs across reboots in <code>/var/log/journal</code>.</p>
<p>The configuration has a deceptively simple trap. Setting <code>Storage=persistent</code> in <code>/etc/systemd/journald.conf</code> is necessary but not sufficient: journald only writes persistently if the directory <code>/var/log/journal</code> actually exists. Create the directory, restart journald, and persistence engages; set the option but skip the directory and the journal silently keeps writing to RAM. <code>SystemMaxUse=300M</code> caps the on-disk journal so logs cannot fill the partition, an important safety valve on production systems.</p>
<p>The boot target is a separate concept that rides along in this task. systemd <b>targets</b> are named groupings of units that represent a system state; <code>multi-user.target</code> is a full multi-user system without a graphical desktop, while <code>graphical.target</code> adds the display manager. The default is a symlink, <code>/etc/systemd/system/default.target</code>, and you set it with <code>systemctl set-default</code>, which is persistent. Do not confuse it with <code>systemctl isolate</code>, which switches the <i>current</i> session&rsquo;s target immediately but reverts at the next boot; using <code>isolate</code> when the task wants a persistent change is a frequent mistake.</p></div>

<h2 id="wt-11" class="pp-h2">Task 11: Configure autofs</h2>

<div class="pp-domain">Domain 5</div>

<div class="pp-deepdive"><div class="pp-deepdive-label">// deep dive</div><p><b>autofs</b> mounts filesystems on demand and unmounts them after a period of inactivity, rather than holding them mounted continuously the way an <code>/etc/fstab</code> entry would. For network shares this is a meaningful advantage: the mount is attempted only when something actually accesses the path, so a temporarily unreachable NFS server cannot hang the boot process or wedge a static mount, and idle shares release automatically.</p>
<p>Configuration is split across two kinds of file. The <b>master map</b>, on RHEL&nbsp;9, a drop-in under <code>/etc/auto.master.d/</code>, associates a base mount point with a map file: <code>/mnt /etc/auto.content</code> says &ldquo;keys defined in <code>/etc/auto.content</code> are mounted under <code>/mnt</code>.&rdquo; The referenced <b>map file</b> then defines the actual mounts. The entry <code>content -rw,sync fileserver&hellip;:/exports/content</code> is an <i>indirect</i> map: the key <code>content</code> becomes the subdirectory <code>/mnt/content</code>, created and mounted only when accessed. (A <i>direct</i> map, by contrast, uses an absolute path as the key and a <code>/-</code> placeholder in the master map.)</p>
<p>The behavior that confuses newcomers is that <code>/mnt/content</code> does not visibly exist until something touches it, listing <code>/mnt</code> alone will not show it and will not trigger the mount. You must access the full path, e.g. <code>ls /mnt/content</code>, to fire the automounter. Note that in this lab the NFS server is fictional, so the autofs configuration can be entirely correct while the mount itself stays empty; on the exam you are graded on the configuration, not on a live remote export.</p></div>
