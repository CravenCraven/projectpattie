<p><span class="c-light">The scenario:</span> You're managing a RHEL 9 server for a growing team. New people join, people leave, roles change, contractors need temporary access, service accounts need to exist but never log in, and someone always ends up with more permissions than they should have. User management sounds basic until you're the one responsible for making sure the right people have the right access and nobody else does.</p>

<p><span class="c-light">The problem:</span> Most tutorials cover <code>useradd</code> and <code>passwd</code> and call it a day. But real user management is deeper than that. It's password policies, account expiration, skeleton directories, group hierarchies, sudo scoping, locking accounts without deleting them, and understanding what happens under the hood when you create a user. If you don't understand the system, you end up with orphaned files, security gaps, and that one contractor account from six months ago that still has sudo access.</p>

<p><span class="c-light">What we're going to do:</span> Go deep on every aspect of user and group management on RHEL 9. Not just the commands but what they actually do to the system, which files they modify, and why each option exists. By the end you'll manage users like someone who understands the machinery, not someone who memorized a cheat sheet.</p>

<h2 id="what-happens-when-you-create-a-user" class="pp-h2">What happens when you create a user</h2>

<h2 id="the-useradd-flags-that-matter" class="pp-h2">The useradd flags that matter</h2>

<p>The bare <code>useradd username</code> command works but it often doesn't give you what you need. Here are the flags you'll use in real life and on the RHCSA:</p>

<div class="pp-code"><div class="pp-code-head"><div class="pp-code-dots"><div class="pp-code-dot" style="background:#ff5f57"></div><div class="pp-code-dot" style="background:#febc2e"></div><div class="pp-code-dot" style="background:#28c840"></div></div><div class="pp-code-lang">bash</div><button class="pp-code-copy" onclick="navigator.clipboard.writeText(this.closest('.pp-code').querySelector('pre').textContent);this.textContent='copied!';setTimeout(()=>this.textContent='copy',1500)">copy</button></div><div class="pp-code-body"><pre>{`# Full-featured user creation\nsudo useradd \\\n  -m \\                    # create home directory\n  -s /bin/bash \\          # set login shell\n  -G developers,wheel \\   # supplementary groups\n  -c "Juan Morales" \\     # full name (GECOS field)\n  -e 2026-12-31 \\         # account expiration date\n  -u 2001 \\               # specific UID\n  jmorales`}</pre></div></div>

<p>Let me explain each one:</p>

<p><code>-m</code> creates the home directory. On RHEL 9 this is the default behavior, but some systems don't create it automatically. Always include it to be safe.</p>

<p><code>-s /bin/bash</code> sets the login shell. Without this, the default is whatever's in <code>/etc/default/useradd</code>, which might be <code>/bin/sh</code> or even nothing. For service accounts that should never log in, use <code>-s /sbin/nologin</code>.</p>

<p><code>-G developers,wheel</code> adds the user to supplementary groups. Capital G. This is different from <code>-g</code> (lowercase) which sets the primary group. The primary group is created automatically with the UPG scheme. Supplementary groups are for shared access.</p>

<p><code>-c "Juan Morales"</code> sets the GECOS field. This is the comment/description that shows up in <code>/etc/passwd</code> and when someone runs <code>finger jmorales</code>. It's just metadata but it helps when you're managing dozens of accounts and can't remember who "jmorales" is.</p>

<p><code>-e 2026-12-31</code> sets an account expiration date. After this date, the user cannot log in. Perfect for contractors or temporary access. The account still exists but it's locked.</p>

<p><code>-u 2001</code> sets a specific UID instead of letting the system auto-assign one. Use this when you need UIDs to match across multiple servers (NFS, for example, relies on matching UIDs).</p>

<h2 id="groups-primary-vs-supplementary" class="pp-h2">Groups. Primary vs supplementary.</h2>

<p>Every user has exactly one primary group and zero or more supplementary groups. This distinction matters more than most people realize.</p>

<p><span class="c-green">Primary group:</span> Determines the default group ownership of files the user creates. When <code>jmorales</code> creates a file, it belongs to <code>jmorales:jmorales</code> (user:primary_group).</p>

<p><span class="c-cyan">Supplementary groups:</span> Determine what shared resources the user can access. Being in the <code>developers</code> group lets you read and write to <code>/opt/projects</code>. Being in the <code>wheel</code> group gives you sudo access.</p>

<div class="pp-code"><div class="pp-code-head"><div class="pp-code-dots"><div class="pp-code-dot" style="background:#ff5f57"></div><div class="pp-code-dot" style="background:#febc2e"></div><div class="pp-code-dot" style="background:#28c840"></div></div><div class="pp-code-lang">bash</div><button class="pp-code-copy" onclick="navigator.clipboard.writeText(this.closest('.pp-code').querySelector('pre').textContent);this.textContent='copied!';setTimeout(()=>this.textContent='copy',1500)">copy</button></div><div class="pp-code-body"><pre>{`# Create groups\nsudo groupadd developers\nsudo groupadd dbadmin\nsudo groupadd monitoring\n\n# Add a user to supplementary groups at creation\nsudo useradd -m -s /bin/bash -G developers,monitoring kpatel\n\n# Add an existing user to more groups (APPEND, don't replace)\nsudo usermod -aG dbadmin kpatel\n\n# Check the result\nid kpatel\n# uid=1002(kpatel) gid=1002(kpatel) groups=1002(kpatel),1001(developers),1003(dbadmin),1004(monitoring)`}</pre></div></div>

<div class="pp-warn"><strong>warning:</strong> The <code>-a</code> flag in <code>usermod -aG</code> means APPEND. If you forget the <code>-a</code> and just run <code>usermod -G dbadmin kpatel</code>, you will REPLACE all supplementary groups with just <code>dbadmin</code>. The user will be removed from <code>developers</code> and <code>monitoring</code>. This is the single most common <code>usermod</code> mistake. Always use <code>-aG</code> together.</div>

<p>Remove a user from a group:</p>

<div class="pp-code"><div class="pp-code-head"><div class="pp-code-dots"><div class="pp-code-dot" style="background:#ff5f57"></div><div class="pp-code-dot" style="background:#febc2e"></div><div class="pp-code-dot" style="background:#28c840"></div></div><div class="pp-code-lang">bash</div><button class="pp-code-copy" onclick="navigator.clipboard.writeText(this.closest('.pp-code').querySelector('pre').textContent);this.textContent='copied!';setTimeout(()=>this.textContent='copy',1500)">copy</button></div><div class="pp-code-body"><pre>{`sudo gpasswd -d kpatel dbadmin\n# Removing user kpatel from group dbadmin`}</pre></div></div>

<h2 id="locking-and-disabling-accounts" class="pp-h2">Locking and disabling accounts</h2>

<p>When someone leaves the company, your first instinct might be to delete their account. Don't. At least not right away. There might be files, running processes, or audit requirements tied to that account. Lock it first, investigate, then delete if appropriate.</p>

<div class="pp-code"><div class="pp-code-head"><div class="pp-code-dots"><div class="pp-code-dot" style="background:#ff5f57"></div><div class="pp-code-dot" style="background:#febc2e"></div><div class="pp-code-dot" style="background:#28c840"></div></div><div class="pp-code-lang">bash</div><button class="pp-code-copy" onclick="navigator.clipboard.writeText(this.closest('.pp-code').querySelector('pre').textContent);this.textContent='copied!';setTimeout(()=>this.textContent='copy',1500)">copy</button></div><div class="pp-code-body"><pre>{`# Lock the account (adds ! to the password hash, preventing login)\nsudo usermod -L jmorales\n\n# Verify the lock\nsudo grep jmorales /etc/shadow\n# jmorales:!$6$hash...:19837:...\n# The ! prefix means locked\n\n# Also expire the account immediately\nsudo chage -E 0 jmorales\n\n# Verify\nsudo chage -l jmorales\n# Account expires: Jan 01, 1970 (effectively immediately)\n\n# Change shell to nologin as a belt-and-suspenders measure\nsudo usermod -s /sbin/nologin jmorales`}</pre></div></div>

<p>Now the account is triple-locked: password is locked, account is expired, and the shell prevents interactive login. Even if someone somehow bypasses one layer, the other two stop them.</p>

<h2 id="service-accounts-users-that-should-never-log-in" class="pp-h2">Service accounts. Users that should never log in.</h2>

<p>Not every user account is for a human. Applications, daemons, and services often need their own user to run under. These accounts should never have a password and should never be able to log in interactively.</p>

<div class="pp-code"><div class="pp-code-head"><div class="pp-code-dots"><div class="pp-code-dot" style="background:#ff5f57"></div><div class="pp-code-dot" style="background:#febc2e"></div><div class="pp-code-dot" style="background:#28c840"></div></div><div class="pp-code-lang">bash</div><button class="pp-code-copy" onclick="navigator.clipboard.writeText(this.closest('.pp-code').querySelector('pre').textContent);this.textContent='copied!';setTimeout(()=>this.textContent='copy',1500)">copy</button></div><div class="pp-code-body"><pre>{`# Create a service account\nsudo useradd \\\n  -r \\                     # system account (UID below 1000)\n  -s /sbin/nologin \\       # no interactive login\n  -d /opt/myapp \\          # home directory is the app directory\n  -M \\                     # do NOT create home directory (it already exists)\n  -c "MyApp Service" \\     # description\n  myapp`}</pre></div></div>

<p>The <code>-r</code> flag creates a system account with a UID below 1000. This is a convention that separates human users (UID 1000+) from service/system accounts (UID below 1000). Tools like <code>getent</code> and login screens often filter based on this.</p>

<p>The <code>-s /sbin/nologin</code> flag means if anyone tries to SSH in as this user or <code>su</code> to it, they get a message saying "This account is currently not available" and the session closes. The service can still run as this user, it just can't be used for interactive access.</p>

<h2 id="deleting-users-properly" class="pp-h2">Deleting users properly</h2>

<p>When it's finally time to delete an account, don't just <code>userdel username</code>. Think about what files that user owned.</p>

<h2 id="checklist" class="pp-h2">Final checklist: monthly access review</h2>

<p>Run this monthly. Seriously. Accounts accumulate access over time and nobody notices until something goes wrong.</p>

<div class="pp-code"><div class="pp-code-head"><div class="pp-code-dots"><div class="pp-code-dot" style="background:#ff5f57"></div><div class="pp-code-dot" style="background:#febc2e"></div><div class="pp-code-dot" style="background:#28c840"></div></div><div class="pp-code-lang">bash</div><button class="pp-code-copy" onclick="navigator.clipboard.writeText(this.closest('.pp-code').querySelector('pre').textContent);this.textContent='copied!';setTimeout(()=>this.textContent='copy',1500)">copy</button></div><div class="pp-code-body"><pre>{`# 1. All users with login shells (should recognize every name)\ngetent passwd | awk -F: '$7 ~ /bash|sh/' | cut -d: -f1\n\n# 2. All users with sudo access (should be minimal)\nsudo grep -r 'ALL=(ALL)' /etc/sudoers /etc/sudoers.d/\n\n# 3. Users who haven't logged in recently (30+ days = investigate)\nsudo lastlog | grep -v "Never logged in" | grep -v Username\n\n# 4. Locked accounts (should match people who left)\nsudo awk -F: '$2 ~ /^!/' /etc/shadow | cut -d: -f1\n\n# 5. Accounts expiring soon\nsudo awk -F: '$8 != "" && $8 != -1' /etc/shadow | cut -d: -f1,8\n\n# 6. Orphaned files (files owned by deleted users)\nsudo find /opt /srv /var/www -nouser -type f 2>/dev/null\n\n# 7. Group memberships (review who's in privileged groups)\ngetent group wheel\ngetent group developers\ngetent group dbadmin`}</pre></div></div>

<p>If any of those checks reveals something unexpected, investigate. A dormant account with wheel access is a security incident waiting to happen. An orphaned file in a web directory could contain sensitive data. Access review is boring but it's one of the most important things you can do as a sysadmin.</p>
