This is the do-it version of the <a href="/blog/ephemeral-vs-persistent-storage">ephemeral vs persistent storage</a> post. You run Postgres twice. The only thing that changes between the two runs is where it writes its data directory. You delete a pod both times and get opposite results.

Every step below shows the command and the output you should see, so you can tell "working" from "stuck" without guessing. The manifests are in the <a href="https://github.com/CravenCraven/k8s-storage-lab">companion repo</a> under <code>manifests/</code>.

## Before you start

You need a running cluster and <code>kubectl</code>. k3s or k3d both work, since both ship <code>local-path</code> as the default StorageClass. Confirm it is there:

  <div className="pp-code-head"><span className="pp-code-dot" /><span className="pp-code-dot" /><span className="pp-code-dot" /><span className="pp-code-lang">bash</span><button className="pp-code-copy">copy</button></div>
  <div className="pp-code-body">{`kubectl get storageclass`}</div>
</div>

<div className="pp-code">
  <div className="pp-code-head"><span className="pp-code-dot" /><span className="pp-code-dot" /><span className="pp-code-dot" /><span className="pp-code-lang">text</span><button className="pp-code-copy">copy</button></div>
  <div className="pp-code-body">{`NAME                   PROVISIONER             RECLAIMPOLICY   VOLUMEBINDINGMODE      AGE\nlocal-path (default)   rancher.io/local-path   Delete          WaitForFirstConsumer   40d`}</div>
</div>

Two columns there matter later. <code>RECLAIMPOLICY: Delete</code> means removing the claim wipes the data. <code>VOLUMEBINDINGMODE: WaitForFirstConsumer</code> means the volume is not created until a pod mounts it. Both show up as "gotchas" further down, except now you will know they are expected.

  <div className="pp-code-body">{`kubectl delete pod -l app=pg-ephemeral\nkubectl rollout status deploy/pg-ephemeral\nkubectl exec deploy/pg-ephemeral -- psql -U postgres -c "select * from notes;"`}</div>
</div>

<div className="pp-code">
  <div className="pp-code-head"><span className="pp-code-dot" /><span className="pp-code-dot" /><span className="pp-code-dot" /><span className="pp-code-lang">text</span><button className="pp-code-copy">copy</button></div>
  <div className="pp-code-body">{`pod "pg-ephemeral-7d9c..." deleted\ndeployment "pg-ephemeral" successfully rolled out\nERROR:  relation "notes" does not exist\nLINE 1: select * from notes;\n                      ^`}</div>
</div>

The table is gone, not empty. Here is what just happened: the new pod got a brand new <code>emptyDir</code>, which is an empty directory. Postgres saw an empty data directory, assumed a fresh install, and ran <code>initdb</code> from scratch. Your table was never on that new disk. This is the failure the concept post opens with, reproduced in about thirty seconds.

## Gotchas and troubleshooting

These are the ones that actually cost me time. Each has a symptom so you can match it to what you are seeing.

<div className="pp-warn">
<b>You deleted the PVC and the data is gone.</b> This is not a bug. <code>local-path</code> defaults to <code>reclaimPolicy: Delete</code>, so removing the claim wipes the directory on the node with no undo. Deleting the pod is safe. Deleting the claim is destructive. Keep them straight.
</div>

<div className="pp-step">
PVC stays <code>Pending</code> and never binds
</div>

If nothing is mounting it, that is expected (<code>WaitForFirstConsumer</code>). If a pod is scheduled and it still will not bind, check that the local-path provisioner is actually running:

<div className="pp-code">
  <div className="pp-code-head"><span className="pp-code-dot" /><span className="pp-code-dot" /><span className="pp-code-dot" /><span className="pp-code-lang">bash</span><button className="pp-code-copy">copy</button></div>
  <div className="pp-code-body">{`kubectl -n kube-system get pods | grep local-path\nkubectl describe pvc pg-data`}</div>
</div>

The <code>describe</code> events at the bottom will tell you what it is waiting on.

<div className="pp-step">
Rollout hangs after an edit, new pod stuck
</div>

Symptom: you change the persistent Deployment, the rollout never finishes, and <code>kubectl get pods</code> shows the new pod stuck in <code>ContainerCreating</code> with a multi-attach error in its events. Cause: a <code>ReadWriteOnce</code> volume can attach to one pod at a time, and the default RollingUpdate tries to start the new pod before the old one lets go. Fix is already in the manifest:

<div className="pp-code">
  <div className="pp-code-head"><span className="pp-code-dot" /><span className="pp-code-dot" /><span className="pp-code-dot" /><span className="pp-code-lang">yaml</span><button className="pp-code-copy">copy</button></div>
  <div className="pp-code-body">{`spec:\n  strategy:\n    type: Recreate`}</div>
</div>

<code>Recreate</code> tears the old pod down before bringing the new one up, so the volume is free when the replacement needs it.

<div className="pp-step">
Persistent Postgres crash-loops on first boot
</div>

Symptom: the pod goes <code>CrashLoopBackOff</code>, and <code>kubectl logs</code> shows <code>initdb</code> refusing because the data directory is not empty. Cause: some volumes hand you a directory that already contains a <code>lost+found</code> from a fresh filesystem. <code>local-path</code> gives you a clean directory so this lab is fine, but on other provisioners point <code>PGDATA</code> at a subdirectory:

<div className="pp-code">
  <div className="pp-code-head"><span className="pp-code-dot" /><span className="pp-code-dot" /><span className="pp-code-dot" /><span className="pp-code-lang">yaml</span><button className="pp-code-copy">copy</button></div>
  <div className="pp-code-body">{`env:\n  - name: PGDATA\n    value: /var/lib/postgresql/data/pgdata`}</div>
</div>

<div className="pp-step">
Other things worth knowing
</div>

- <code>emptyDir</code> survives a container crash inside the pod. It does not survive a pod delete, a node drain, or a reschedule. It is not the safety net people assume.
- <code>local-path</code> pins data to one node. The PV carries node affinity, so the pod is forced back to the node holding the disk. On multiple nodes it cannot move freely, and if that node's disk dies the data dies with it. No replication.
- The size request is not a hard limit. <code>requests.storage: 1Gi</code> is recorded on the PVC, but <code>local-path</code> does not enforce it. You can write past it until the node's real disk fills.

## Cleanup

<div className="pp-code">
  <div className="pp-code-head"><span className="pp-code-dot" /><span className="pp-code-dot" /><span className="pp-code-dot" /><span className="pp-code-lang">bash</span><button className="pp-code-copy">copy</button></div>
  <div className="pp-code-body">{`kubectl delete -f manifests/01-ephemeral-postgres.yaml\nkubectl delete -f manifests/03-persistent-postgres.yaml\nkubectl delete -f manifests/02-pvc.yaml\nkubectl get pvc,pv`}</div>
</div>

The last command should return nothing for these resources. Deleting the PVC releases the PV, and <code>local-path</code> removes the directory on the node.
