<h1 class="pp-title">Secrets Are Just Base64<br/><em>and Other Lies I Believed</em></h1>

<p class="pp-subtitle">My tunnel credentials only existed because I typed them in one night. Getting them into Git, encrypted, meant finding out how many things I was confidently wrong about.</p>

## The hook

My repo has one rule: if it is not in `main`, it is not in the cluster. In my
last post I broke it on purpose. The Cloudflare Tunnel credentials went in with
`kubectl create secret`, typed by hand, and if I rebuilt the cluster from Git
tomorrow the tunnel would not come back. I wrote "Sealed Secrets is on my
roadmap" and moved on.

It did not stay on the roadmap long. It also turned out I was wrong about
almost every part of how secrets work, starting with whether they are secret.

## What I built and why

Secrets that live in Git, encrypted, and get unlocked by Flux on the way into
the cluster. I went with SOPS and age instead of Sealed Secrets.

First thing I had wrong. I thought a Kubernetes Secret was encrypted. It is
base64. That is not encryption, it is just a different way of writing the same
text, and anyone can turn it back with one command and no password. Pushing a
normal Secret to GitHub is pushing the password with extra steps.

So the job is a lock and a key:

- **The public key** can only lock things. It sits in the repo and that is fine,
  because it cannot open anything.
- **The private key** is the only thing that can unlock. It lives inside the
  cluster and never goes near Git.

What happens to a secret now:

```
my laptop (plain file) -> sops locks it -> GitHub -> Flux pulls it -> unlocks with the private key -> Secret in cluster -> pod
```

I did it twice. Once to take over the tunnel credentials, and once so Linkding
creates its own admin user. Until now I had been running `createsuperuser`
inside the pod by hand, which is exactly the kind of thing that does not
survive a rebuild.

## Before you start

- A k3s cluster with Flux already running
- `kubectl` working from your laptop
- `sops` and `age` installed. On a Mac that is `brew install sops age`
- A secret you made by hand and are a little embarrassed about

Run everything from the root of the repo. SOPS looks for its rules file in the
folder you are standing in, and if you are in the wrong one it has no idea what
to do.

## How I did it

**Make the key pair.**

```bash
age-keygen -o <path-to-age-key>
```

This prints the public key, which starts with `age1`, and writes the private
key to the file. That file stays off GitHub forever.

**Write the rules file.** `.sops.yaml` at the root of the repo:

```yaml
creation_rules:
  - path_regex: .*\.yaml
    encrypted_regex: ^(data|stringData)$
    age: <age-public-key>
```

`path_regex` is which files this applies to. `encrypted_regex` is which parts
of them get locked, and it is only the values under `data` and `stringData`.
The `kind`, `name` and `namespace` stay readable on purpose. Flux needs to know
what the thing is before it can unlock it.

**Give the cluster the private key.**

```bash
kubectl create secret generic sops-age -n flux-system --from-file=age.agekey=<path-to-age-key>
```

Yes, this is a secret made by hand. It has to be. It is the key to every other
secret, so something has to exist before Git can take over. One hand-made
secret instead of all of them.

**Tell Flux to unlock.** On the Flux Kustomization that applies my apps:

```yaml
decryption:
  provider: sops
  secretRef:
    name: sops-age
```

Second thing I had wrong. I assumed this would flow down from the top
Kustomization to everything underneath. It does not. It has to sit on the one
that actually applies the secret files. My setup has three Kustomizations
chained across two repos, so "which one" took a minute. All my app folders get
applied by one called `apps`, so that is where it went.

**Put the secret next to the app.**

Third thing. My first idea was to put the secret at the root of the repo so it
would apply to everything. A Secret does not apply to everything. It belongs to
one namespace, and only pods in that namespace can read it. So it goes in the
app's own folder.

```bash
grep -rl linkding apps
```

Lists every file that mentions the app, which tells you where its folder is.

**Write it in plain text first.** `apps/base/linkding/secret.yaml`:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: linkding-superuser
  namespace: linkding
type: Opaque
stringData:
  LD_SUPERUSER_NAME: op
  LD_SUPERUSER_PASSWORD: "<password>"
```

`stringData` lets me type the values as they are. `data` would mean base64-ing
them myself first. My first name for this secret had a space in it, and
Kubernetes said no. Lowercase, numbers and hyphens only.

To look at it without putting the password on my screen:

```bash
grep -v PASSWORD apps/base/linkding/secret.yaml
```

`-v` flips grep around, so it prints every line except the ones that match.

**Lock it.**

```bash
sops --encrypt --in-place apps/base/linkding/secret.yaml
```

`--in-place` overwrites the file with the locked version. No output means it
worked.

Fourth thing, and this one is my favourite. Right before running that, I asked
"didn't I do encryption yesterday?" I had. On a different file. The setup
happens once. Every new secret file gets locked on its own. I had locked one
box and assumed it covered the next box too.

**Check it is actually locked.**

```bash
grep -c "ENC\[" apps/base/linkding/secret.yaml
```

That counts the lines SOPS has marked as encrypted. Mine said 3. Two values,
plus one SOPS adds itself so it can tell if anyone has tampered with the file.

**List it.** Add `secret.yaml` under `resources:` in the folder's
`kustomization.yaml`. Flux does not apply a file just because it is in the
folder.

**Point Linkding at it.** In the container, lined up with `ports:`:

```yaml
envFrom:
  - secretRef:
      name: linkding-superuser
```

`envFrom` turns every key in the secret into an environment variable with the
same name. I named mine exactly what Linkding looks for, so one block loads
both.

**Check it builds before pushing.**

```bash
kubectl kustomize apps/base/linkding | grep -A3 envFrom
```

This builds the folder the way Flux will, on my laptop, without touching the
cluster. If the YAML is broken I find out here instead of from a pod that will
not start.

**Commit just those files.**

```bash
git add apps/base/linkding/secret.yaml apps/base/linkding/kustomization.yaml apps/base/linkding/deployment.yaml
git commit -m "feat(linkding): create superuser from encrypted secret"
git push
```

Naming the files instead of `git add .` means nothing extra sneaks in. That is
also the commit message I should have written. More on that later.

**Make Flux pick it up now.**

```bash
flux reconcile kustomization apps --with-source
```

`--with-source` pulls from GitHub first, instead of me waiting ten minutes for
the next sync.

**Then the tunnel credentials.** Same steps, but the file had the same name and
namespace as the secret already sitting in the cluster. Flux applied it, and I
checked:

```
NAME                 TYPE     DATA   AGE
tunnel-credentials   Opaque   1      41h
```

Fifth thing. I expected that to be new. It was not. Flux found a secret with
the same name already there and updated it in place, and AGE counts from when
something was created, not when it last changed. Repainting a house does not
change the year it was built.

Which meant I could not tell whether that secret existed because of me or
because of Git. So I deleted it.

```bash
kubectl delete secret tunnel-credentials -n cloudflared
flux reconcile kustomization apps --with-source
kubectl get secrets -n cloudflared
```

```
NAME                 TYPE     DATA   AGE
tunnel-credentials   Opaque   1      38s
```

38 seconds. Git put it back without me. That is the whole point of doing any of
this.

## What broke and how I fixed it

**Vim ate my indentation.** I pasted the `envFrom` block and vim auto-indented
every line, so `envFrom` ended up nested under `ports` and the next two lines
slid off to the left edge. I tried `:set paste`, which only works if you turn
it on before you paste. Not after. What fixed it was `<<` and `>>` in command
mode, which move a whole line left or right without retyping it. I lined each
one up against the line above and ran `kubectl kustomize` again to make sure it
parsed.

**grep could not find a name I knew was there.** I searched the encrypted file
for `^  name:`, two spaces then `name:`, and got nothing back. SOPS had
rewritten the file with four spaces when it encrypted it. I dropped the spacing
and it found it straight away:

```bash
grep -nE "name:|namespace:" apps/base/cloudflared/secret.yaml
```

**Linkding would not create my user.** The log said:

```
INFO Skip creating initial superuser, user already exists
```

Not actually broken. Those variables only create a user on a fresh install with
an empty database. I already had one, so Linkding left it alone, which is the
right call. The thing to remember is the other side of it: changing the
password in the secret later will not change my existing login.

**I reused yesterday's commit message.** Word for word. My Linkding commit says
it encrypts the tunnel credentials. It was already pushed to `main`, and
rewriting pushed history to fix a typo-level mistake is a worse habit than the
mistake. So it stays.

## How I checked it worked

**The tunnel.** Running pods keep the copy of a secret they loaded when they
started, so until they restart I have not proven anything:

```bash
kubectl rollout restart deployment cloudflared -n cloudflared
kubectl get pods -n cloudflared
```

Two new pods, `1/1 Running`, and the Linkding URL loaded in the browser. That
means the tunnel is running on credentials that came out of Git.

**Linkding.** Three checks:

```bash
kubectl get pods -n linkding
kubectl exec deploy/linkding -n linkding -- printenv LD_SUPERUSER_NAME
kubectl logs deploy/linkding -n linkding | grep -i superuser
```

The pod was new and running. `printenv` printed `op`, so the variable made it
into the container. I only ever print the username, never the password. And the
log line from earlier shows Linkding read the variables and decided what to do
with them.

## How my answer compared to the course's

After I finished, I checked my work against the course solution. Same result
in the cluster, different roads to it. Here is each difference, and why it
matters.

**He generated the secret file. I typed mine.**

```bash
kubectl create secret generic linkding-superuser -n linkding --from-literal=LD_SUPERUSER_NAME=op --from-literal=LD_SUPERUSER_PASSWORD=<password> --dry-run=client -o yaml > secret.yaml
```

`--dry-run=client` builds the secret on your laptop and stops before sending it
to the cluster. `-o yaml` prints it as YAML, and `>` saves it into a file. So
kubectl fills in the form for you, with no typos and no broken indentation.
That would have saved me the whole vim episode.

The catch is `--from-literal`. It puts the password on the command line, which
means it lands in your shell history. Typing it into the file in vim kept it
out of there. And writing it by hand is how I learned what every line in a
Secret is for, which is what you need when one breaks.

The trick works for nearly anything, not just secrets. It is the quickest way
to get a correct skeleton for a deployment or a configmap.

**His file used `data`. Mine used `stringData`.** That is a side effect of the
first difference. kubectl writes the values under `data`, already base64.
I used `stringData`, which takes plain text and lets Kubernetes do the encoding
when it stores it. Once they are in the cluster they are identical. `stringData`
is for people typing. `data` is what tools produce.

**He gave SOPS its rules every time. Mine are written down once.**

```bash
sops --age=<age-public-key> --encrypt --encrypted-regex '^(data|stringData)$' --in-place secret.yaml
```

That is his. Mine is just `sops --encrypt --in-place`, because the key and the
regex live in `.sops.yaml` and SOPS reads it when I run it from the repo. Same
key, same fields, same result. The difference is memory. His way means typing a
long key and a regex every time, and if you forget the regex once, SOPS locks
the whole file, `kind` and `name` included, and Flux cannot even tell it is a
Secret anymore. Mine is written down once, in the repo, and anyone who clones it
encrypts the same way. Remembering long commands is genuinely the hard part for
me, so this one is not close.

**He loaded a ConfigMap as well. I did not need one.** His `envFrom` pulls from
a ConfigMap and a Secret. A ConfigMap holds settings that are not sensitive,
like a timezone. A Secret holds the ones that are. His Linkding already had a
ConfigMap from an earlier step and mine does not, so there was nothing for me
to load. Not a missed step, just a different starting point.

**I tested more.** The solution shows the files and the commands. I deleted the
secret and watched it come back, restarted the pods, and checked `printenv` and
the logs. "The file is in Git" and "Git is where the secret comes from" are not
the same claim, and until you delete and rebuild, the hand-made one could still
be the one doing the work.

The course also links the twelve-factor app's page on config, and that is the
why behind `envFrom`. Anything that changes between environments, like
passwords, URLs and usernames, goes in environment variables instead of being
baked into the app. Same image, different secret, different environment.

## What I learned

**Base64 is not security.** A plain Secret can be read by anyone who can read
the file. With SOPS the repo holds a locked box, and the only key that opens it
lives in the cluster. The public key is safe to commit because all it can do is
lock.

**"Flux applied it" is not the same as "Git owns it".** The secret existing
told me nothing about where it came from. Deleting it and watching it come back
was the proof. Then restarting the pods, because they were still holding the
old copy.

**Setup is once, encrypting is every time, and settings do not inherit.** The
key, the rules file and the decryption block are done once. Every new secret
file gets its own `sops --encrypt`. And the decryption setting has to be on the
exact Kustomization that applies the file, not somewhere above it.

## What I would do next

- **Back up the private key.** It is on my laptop and in the cluster. If I lose
  both, every secret in the repo is locked for good. Extremely secure. Not
  useful.
- **Work out why the tunnel pods both vanished.** During the restart, `get
  pods` showed nothing at all for a few seconds. It has two replicas and should
  swap them one at a time. It came back fine, but I want the actual reason, not
  "it came back fine".
- **Do the same for every new app** as I add them, so the `sops-age` key really
  is the only thing in the cluster I typed by hand.
