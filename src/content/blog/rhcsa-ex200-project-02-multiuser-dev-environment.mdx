<div class="pp-brief"><p><span class="c-light">Scenario:</span> Your team needs a shared development server on <code>devserver1.lab.example.com</code>. You create user accounts with the right group memberships, set up shared storage with correct permissions, configure sudo access, enforce password policies, automate user reporting with a shell script, and make sure the environment is auditable after a reboot.</p><p><span class="c-light">Domains Covered:</span> All 6 (D1 through D6)</p><p><span class="c-light">Estimated Time:</span> 90–120 minutes</p><p><span class="c-light">Difficulty:</span> Exam-level</p><p><span class="c-light">Rule:</span> Every configuration must survive a reboot. Verify after rebooting.</p></div>

<div class="pp-note"><strong>note:</strong> You need a clean RHEL 9 VM with root access, one extra unpartitioned disk at <code>/dev/sdb</code> for Task 3, and internet access for <code>dnf</code>. Two hostnames here are lab placeholders: <code>repo.lab.example.com</code> in Task 9 and <code>fileserver.lab.example.com</code> in Task 10. You configure them exactly as shown, but the package install only completes against a real mirror (point <code>baseurl</code> at your own repositories if you want it to succeed), and the autofs mount stays empty without a matching NFS export. The configuration itself is what gets graded. That is expected.</div>

<div class="pp-part" id="p1">Part 1: The Exam<small>Attempt every task on your own first. Every configuration must survive a reboot.</small></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 1: Create users and groups</h3><div class="pp-domain">Domain 1</div><p>Create the following groups and users:</p><ul><li>Group <code>developers</code> (GID 7000)</li><li>Group <code>ops</code> (GID 7001)</li><li>Group <code>contractors</code> (GID 7002)</li><li>User <code>dev1</code> (UID 7001, primary group: <code>developers</code>, shell: <code>/bin/bash</code>)</li><li>User <code>dev2</code> (UID 7002, primary group: <code>developers</code>, shell: <code>/bin/bash</code>)</li><li>User <code>ops1</code> (UID 7003, primary group: <code>ops</code>, shell: <code>/bin/bash</code>)</li><li>User <code>contractor1</code> (UID 7004, primary group: <code>contractors</code>, supplementary group: <code>developers</code>, shell: <code>/bin/bash</code>)</li></ul><p>Set the password <code>Dev@12345!</code> for all four users.</p></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 2: Configure password policies</h3><div class="pp-domain">Domain 1</div><p>Using <code>chage</code>, configure the following for <code>dev1</code> and <code>dev2</code>:</p><ul><li>Password expires every 90 days</li><li>Warning issued 10 days before expiry</li><li>Account locks 5 days after password expires</li></ul><p>Configure <code>/etc/security/pwquality.conf</code> to enforce system-wide:</p><ul><li>Minimum password length: 12 characters</li><li>At least 1 uppercase letter</li><li>At least 1 digit</li><li>At least 1 special character</li></ul></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 3: Set up shared project storage</h3><div class="pp-domain">Domain 4 + Domain 5</div><p>Create a 1 GiB LVM Logical Volume named <code>lv_projects</code> in a new Volume Group <code>vg_dev</code> using <code>/dev/sdb</code>. Format it as XFS. Mount it persistently at <code>/projects</code> using its UUID in <code>/etc/fstab</code>.</p><p>Set ownership to <code>root:developers</code> and permissions to <code>2770</code> (setGID bit set) so all files created inside inherit the <code>developers</code> group. Create two subdirectories:</p><ul><li><code>/projects/shared</code>: accessible by both <code>developers</code> and <code>ops</code> (use ACLs)</li><li><code>/projects/private</code>: accessible only by <code>developers</code></li></ul></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 4: Configure ACLs on shared storage</h3><div class="pp-domain">Domain 5</div><p>On <code>/projects/shared</code>:</p><ul><li>Give group <code>developers</code> read/write/execute</li><li>Give group <code>ops</code> read/execute only (no write)</li><li>Set default ACLs so new files inherit the same permissions</li></ul><p>On <code>/projects/private</code>:</p><ul><li>Give group <code>developers</code> read/write/execute</li><li>Give group <code>ops</code> no access</li><li>Verify with <code>getfacl</code></li></ul></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 5: Configure sudo access</h3><div class="pp-domain">Domain 1</div><p>Create the file <code>/etc/sudoers.d/developers</code> so that:</p><ul><li>All members of <code>developers</code> can run any command as root without a password</li><li>All members of <code>ops</code> can run only <code>/bin/systemctl</code> and <code>/usr/bin/journalctl</code> as root, with password required</li></ul><p>Use <code>visudo -f</code> to validate the file. Do not edit <code>/etc/sudoers</code> directly.</p></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 6: Write a user activity report script</h3><div class="pp-domain">Domain 2</div><p>Create an executable script at <code>/usr/local/bin/user_report.sh</code> that:</p><ul><li>Loops through all users with UID &gt;= 1000 and &lt; 65534</li><li>For each user prints: username, UID, primary group, home directory (exists or MISSING), and last login time</li><li>Outputs a summary line at the end: <code>Total regular users: N</code></li><li>Saves the report to <code>/var/log/user_report.txt</code> with a timestamp header</li><li>Exits with code 0 on success, code 1 if the report file cannot be written</li></ul></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 7: Schedule the report</h3><div class="pp-domain">Domain 6</div><p>Schedule <code>/usr/local/bin/user_report.sh</code> to run:</p><ol><li>Every Monday at 6:00 AM via a root crontab entry</li><li>At system boot (after the network is available) via a systemd service unit at <code>/etc/systemd/system/user-report.service</code></li></ol><p>Enable the systemd service so it runs on every boot.</p></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 8: Configure system logging and journal</h3><div class="pp-domain">Domain 3</div><p>Configure <code>rsyslog</code> to write all <code>authpriv</code> messages (auth/sudo events) to <code>/var/log/auth_audit.log</code>. Configure the system journal to be persistent with a maximum size of 400M. Restart both <code>rsyslog</code> and <code>systemd-journald</code>. Verify by running a <code>sudo</code> command as <code>dev1</code> and confirming the event appears in <code>/var/log/auth_audit.log</code>.</p></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 9: Install development tools and configure a local repo</h3><div class="pp-domain">Domain 6</div><p>Create a local DNF repo file at <code>/etc/yum.repos.d/devtools.repo</code> pointing to <code>http://repo.lab.example.com/rhel9/AppStream</code> with GPG check disabled. Install the <code>Development Tools</code> package group and the <code>git</code> and <code>python3</code> packages. Verify installation with <code>gcc --version</code>, <code>git --version</code>, and <code>python3 --version</code>.</p></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 10: Configure autofs for developer home directories</h3><div class="pp-domain">Domain 5</div><p>Configure autofs with an indirect wildcard map so that accessing <code>/mnt/devhomes/&lt;username&gt;</code> automatically mounts <code>fileserver.lab.example.com:/devhomes/&lt;username&gt;</code>. Enable and start the autofs service. Test by accessing <code>/mnt/devhomes/dev1</code>.</p></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 11: Set the hostname and configure NTP</h3><div class="pp-domain">Domain 6</div><p>Set the system hostname to <code>devserver1.lab.example.com</code>. Configure <code>chronyd</code> to use <code>time.cloudflare.com iburst</code>. Set the timezone to <code>America/Chicago</code>. Verify NTP is syncing and the hostname is correct after reboot.</p></div>

<div class="pp-exam-task"><h3 class="pp-h3">Task 12: Reboot and verify everything</h3><div class="pp-domain">All Domains</div><p>Reboot the system and confirm every configuration survived. Run through the verification checklist in the Outcomes section.</p></div>

<h2 id="wt-03" class="pp-h2">Task 3: Set up shared project storage</h2>

<div class="pp-domain">Domain 4 + Domain 5</div>

<div class="pp-deepdive"><div class="pp-deepdive-label">// deep dive</div><p>The storage stack here is the standard LVM chain, physical volume, volume group, logical volume, filesystem, but the interesting part is the permission model. In a shared directory the usual problem is that each user creates files owned by their own primary group, so collaborators cannot edit each other's work. The fix is the <b>setGID</b> bit on the directory.</p><p><code>chmod 2770</code> sets three things at once. The <code>7</code> gives the owning user full access, the second <code>7</code> gives the owning group full access, the <code>0</code> denies everyone else, and the leading <code>2</code> sets setGID. On a directory, setGID means every file and subdirectory created inside inherits the directory's group rather than the creator's primary group. It also propagates: a new subdirectory inherits both the group and the setGID bit, which is why <code>/projects/shared</code> and <code>/projects/private</code> pick up the <code>developers</code> group automatically.</p><p>Order matters. Set the group ownership with <code>chown root:developers</code> first, then <code>chmod 2770</code>, otherwise the setGID bit attaches to whatever group the directory happened to have.</p></div>

<h2 id="wt-04" class="pp-h2">Task 4: Configure ACLs on shared storage</h2>

<div class="pp-domain">Domain 5</div>

<div class="pp-deepdive"><div class="pp-deepdive-label">// deep dive</div><p>Standard Unix permissions give you exactly three sets of rights: owner, one group, and everyone else. The moment two different groups need different access to the same directory, that model runs out of room. POSIX ACLs add named entries on top, so you can say developers get rwx and ops get r-x on the same folder.</p><p>A <code>getfacl</code> listing has a fixed grammar. <code>user::</code> and <code>group::</code> are the owning user and owning group (the same bits you see in <code>ls -l</code>). <code>user:name:</code> and <code>group:name:</code> are named entries. <code>other::</code> is everyone else. The <code>mask::</code> entry is a ceiling: it caps the effective permission of every named entry and the owning group, so if the mask is <code>r-x</code> a named <code>rwx</code> entry is effectively only <code>r-x</code>.</p><p>The key insight for this task is that <code>developers</code> is the <b>owning group</b>, so it is represented by the <code>group::</code> entry that comes from the <code>2770</code> bits. You do not need a named <code>group:developers</code> ACL at all; you only add a named entry for <code>ops</code>. Finally, ACLs apply only to files that exist now. To make new files inherit the rules you set a <b>default</b> ACL with <code>setfacl -d</code>, which acts as a template for anything created later inside the directory.</p></div>

<p><b>Goal:</b> On <code>/projects/shared</code>, developers get read/write/execute and ops get read/execute; on <code>/projects/private</code>, ops get nothing. New files must inherit these rules.</p><h4 class="pp-step">Step 4.1: Shared directory</h4><div class="pp-code"><div class="pp-code-head"><div class="pp-code-dots"><div class="pp-code-dot" style="background:#ff5f57"></div><div class="pp-code-dot" style="background:#febc2e"></div><div class="pp-code-dot" style="background:#28c840"></div></div><div class="pp-code-lang">bash</div><button class="pp-code-copy" onclick="navigator.clipboard.writeText(this.closest('.pp-code').querySelector('pre').textContent);this.textContent='copied!';setTimeout(()=>this.textContent='copy',1500)">copy</button></div><div class="pp-code-body"><pre>{`# developers already have rwx as the owning group (the 2770 above)\nsetfacl -m g:ops:r-x /projects/shared\nsetfacl -m o::--- /projects/shared\n\n# default ACLs so new files inherit the same access\nsetfacl -d -m u::rwx,g::rwx,g:ops:r-x,o::--- /projects/shared`}</pre></div></div><p>Because <code>developers</code> is the directory&#x27;s owning group, its <code>rwx</code> comes from the standard group permission bits; you only need a named ACL for <code>ops</code>. <h2 id="wt-05" class="pp-h2">Task 5: Configure sudo access</h2>

<div class="pp-domain">Domain 1</div>

<div class="pp-deepdive"><div class="pp-deepdive-label">// deep dive</div><p>A sudoers rule reads as four parts: <code>who  where = (run-as)  what</code>. So <code>%developers ALL=(ALL) NOPASSWD: ALL</code> means members of the developers group, on any host, may run any command as any user, without a password. The leading <code>%</code> is what makes it a group rule rather than a single user. The ops line lists explicit absolute command paths instead of <code>ALL</code>, which limits that group to exactly those binaries, and because it omits <code>NOPASSWD</code> it still prompts for the user's own password.</p><p>Never edit <code>/etc/sudoers</code> by hand. The bottom of that file contains <code>#includedir /etc/sudoers.d</code>, so dropping a file there is the supported, modular way to add rules. Two hard requirements: the file must be mode <code>0440</code> or sudo refuses to read it, and the syntax must be valid or you can lock everyone out of sudo. <code>visudo -f</code> edits a drop-in with a syntax check on save, and <code>visudo -c</code> validates without opening an editor.</p><p>One RHEL 9 trap: use <code>/usr/bin/systemctl</code>, not <code>/bin/systemctl</code>. <code>/bin</code> is a symlink to <code>/usr/bin</code>, but sudo matches the command against the path it actually resolves, which is the <code>/usr/bin</code> form, so the <code>/bin</code> spelling can silently fail to match.</p></div>

<h2 id="wt-10" class="pp-h2">Task 10: Configure autofs for developer home directories</h2>

<div class="pp-domain">Domain 5</div>

<div class="pp-deepdive"><div class="pp-deepdive-label">// deep dive</div><p>You could mount every developer home with a permanent <code>/etc/fstab</code> entry, but that mounts everything at boot whether or not anyone uses it, and it does not scale to dozens of nearly identical mounts. <code>autofs</code> mounts on demand and unmounts again after a period of inactivity, which is lighter and self-healing.</p><p>autofs is configured in two layers. Because the mount is created on access, listing the parent <code>/mnt/devhomes</code> shows nothing; you must reference a specific subdirectory to trigger it.</p></div>

Without a matching NFS export the mount stays empty, but the configuration is what the exam grades. <h2 id="wt-11" class="pp-h2">Task 11: Set the hostname and configure NTP</h2>

<div class="pp-domain">Domain 6</div>

<div class="pp-deepdive"><div class="pp-deepdive-label">// deep dive</div><p><code>hostnamectl set-hostname</code> writes the name to <code>/etc/hostname</code>, so it is the persistent way to rename a host. The older <code>hostname</code> command only changes the running value and is lost on reboot. systemd actually tracks three hostnames, static (the configured one), transient (a DHCP or runtime value), and pretty (a free-form label), but for the exam the static one set by <code>hostnamectl</code> is what counts. Adding the name to <code>/etc/hosts</code> lets the machine resolve its own fully-qualified name without depending on DNS, which some services expect.</p><p>Time on RHEL 9 is handled by <code>chrony</code>. You point it at a source with a <code>server</code> line in <code>/etc/chrony.conf</code>; the <code>iburst</code> option makes the first sync happen quickly by sending a short burst of probes. Comment out the default pool and server lines before adding your own so chrony is not also averaging in the shipped sources. <code>chronyc sources</code> shows the candidates, where a <code>^\*</code> marks the currently selected source, and <code>chronyc tracking</code> shows how closely the clock is disciplined. Timezone is separate from sync: <code>timedatectl set-timezone</code> repoints <code>/etc/localtime</code> at the right zone file.</p></div>

<p><b>Goal:</b> Persistent hostname, correct timezone, and a working time source.</p><h4 class="pp-step">Step 11.1: Hostname</h4><div class="pp-code"><div class="pp-code-head"><div class="pp-code-dots"><div class="pp-code-dot" style="background:#ff5f57"></div><div class="pp-code-dot" style="background:#febc2e"></div><div class="pp-code-dot" style="background:#28c840"></div></div><div class="pp-code-lang">bash</div><button class="pp-code-copy" onclick="navigator.clipboard.writeText(this.closest('.pp-code').querySelector('pre').textContent);this.textContent='copied!';setTimeout(()=>this.textContent='copy',1500)">copy</button></div><div class="pp-code-body"><pre>{`hostnamectl set-hostname devserver1.lab.example.com\necho '127.0.0.1  devserver1.lab.example.com devserver1' >> /etc/hosts`}</pre></div></div><p><code>hostnamectl</code> writes the change to <code>/etc/hostname</code> so it survives reboot. Adding the name to <code>/etc/hosts</code> lets the box resolve its own fully-qualified name without DNS.</p><h4 class="pp-step">Step 11.2: Timezone and time source</h4><div class="pp-code"><div class="pp-code-head"><div class="pp-code-dots"><div class="pp-code-dot" style="background:#ff5f57"></div><div class="pp-code-dot" style="background:#febc2e"></div><div class="pp-code-dot" style="background:#28c840"></div></div><div class="pp-code-lang">bash</div><button class="pp-code-copy" onclick="navigator.clipboard.writeText(this.closest('.pp-code').querySelector('pre').textContent);this.textContent='copied!';setTimeout(()=>this.textContent='copy',1500)">copy</button></div><div class="pp-code-body"><pre>{`timedatectl set-timezone America/Chicago\n\nsed -i 's/^pool/#pool/'   /etc/chrony.conf\nsed -i 's/^server/#server/' /etc/chrony.conf\necho 'server time.cloudflare.com iburst' >> /etc/chrony.conf\n\nsystemctl restart chronyd\nchronyc sources -v`}</pre></div></div><p>Comment out the default sources before adding yours, so chrony does not average your chosen server against the ones it is still polling.</p><div class="pp-note"><strong>checkpoint:</strong> <code>hostname</code> returns <code>devserver1.lab.example.com</code>, and <code>timedatectl</code> shows <code>America/Chicago</code> with the clock synchronized.</div>

<h2 id="wt-12" class="pp-h2">Task 12: Reboot and verify everything</h2>

<div class="pp-domain">All Domains</div>

<div class="pp-deepdive"><div class="pp-deepdive-label">// deep dive</div><p>The reboot is not a formality, it is the actual test. Almost every way to fail this kind of exam comes down to the same mistake: a setting that is correct in memory right now but was never written somewhere that survives a restart.</p><p>It helps to sort each task into one of two buckets. <b>On-disk</b> state persists by nature: an <code>/etc/fstab</code> line, ACLs stored in the filesystem, a sudoers drop-in, a script on disk, the contents of <code>/etc/chrony.conf</code>. <b>Runtime</b> state does not: a service you started but never enabled, a hostname set with the wrong command, an fstab you edited but never tested with <code>mount -a</code>.</p><p>The two verbs that catch most of it are <code>enable</code> (start at every boot) versus <code>start</code> (start right now), and <code>daemon-reload</code> so systemd actually reads a new unit file before you enable it. Reboot, then walk the checklist one line at a time. If something is missing, you know it was runtime-only, and you go back and make it persistent.</p></div>
